## 0.5. Design decisions (ruled by the operator 2026-09-21 — constraints, not options)

**S4-D1 — Custody widening.** Widen S3's three checkpoint tables from `attempt_id PRIMARY KEY` + `CHECK(checkpoint='N1')` to `PRIMARY KEY(attempt_id, checkpoint)` + `CHECK(checkpoint IN ('N1','N2','PART_A'))` **once**, as DB `user_version` 9 with exact layout validation (the closed three-checkpoint set so S5 needs no further layout change; the service still admits only what the installed release dispatches). Consequence for T05: its result/seal tables become `user_version` 10 at integration (one-line seam in its `_ensure_result_layout`; T05 is accepted after T04 anyway). Column names unchanged (T05's accessor). *Alternative rejected:* per-slice versions 9/10/11 with three migrations.

**S4-D2 — Joint batch as one capture with two decisions.** One `n2_worker` run produces FULL at the frozen N2 depth and H1/H2 at the frozen PART_B depth in one framed result (`qualification_worker_result/v1` records gain `stage ∈ {'N2','PART_B'}` with population/path indices; N1 bytes unchanged). One capture, one attestation, **one assessment** carrying `stage_decisions = {N2: PASS|FAIL, PART_B: PASS|FAIL}` and the campaign `decision` (`CONTINUE` only when both PASS → `PART_A_READY`; otherwise `FAILURE` → `N2_FAILED`), one checkpoint receipt binding the exact committed N1 receipt as predecessor. The family stays `/v1` with **checkpoint-keyed closed field sets** (`stage_decisions` required for `N2`, forbidden for `N1`; the N1 pinned vectors are unchanged). Snapshot `/v7` = `/v6` with `checkpoints` keys ⊆ {`N1`,`N2`} and the N2 entry carrying `stage_decisions`; budget-profile v3 pairs v5–v7. *Alternative rejected:* a separate PART_B execution identity or a second assessment (spec §2.3 forbids an independent PART_B verdict; the slice: "the service stores one N2 execution identity, not a PART_B execution").

**S4-D3 — Release/profile.** One new literal `qualification_execution_release/v6` + profile `/v6` with `supported_checkpoints = dispatch_checkpoints = ['N1','N2']`, TEST_ONLY, `production_execution=False`; v5 keeps N1-only (`['N1']` exactly), v3/v4 keep refusing dispatch; fresh attempts only. *Alternative rejected:* mutating v5's closed set (would re-open accepted S3 bytes).

**S4-D4 — Continuation policy under a versioned FULL_E1 policy identity.** `required_output_roles` accepts `(stages == order[:4], ('PARTIAL','NONE'))` only under the FULL_E1 policy/schema identity introduced here (the policy fingerprint changes, so the installed fixture/manifest producers and every earlier-stage consumer are re-pinned in the same change); N1_ONLY retains its rejection. *Alternative rejected:* accepting the joint prefix under the existing policy identity (would silently change what already-admitted N1_ONLY attempts mean).

## 3. Behavior (binding)
After a committed N1 PASS (`N2_READY`), exactly one worker produces the joint batch; G5 commits both decisions from that same batch; both PASS → `PART_A_READY`; either FAIL → `N2_FAILED` (a legal statistical-FAIL prefix, eligible for S6's later FAIL commit); no Part A dispatch ever follows a FAIL. Missing halves, changed order/count/seed, FULL substituted for the speed sample, a replayed or stale predecessor, a batch whose N1 receipt is not the committed one — all refuse with a reason string. Crash after START_INTENT without capture → IN_DOUBT; after capture → recover saved bytes only; signing-intent/retry semantics as S3. A3 inherited (restart mid-N2 → IN_DOUBT). Every payload uses the handshake; the g5 unit sits in the payload slice.
