Q7 measures the gap. So **every incident must reach Joshua through the Important rule set**, or neither the push nor the call fires.
3. **What "important" is in Grafana IRM** (public docs, §13). Importance is a property of the escalation step: a notify step uses "Default notifications or Important notifications" [S4]. No public page read for this card documents a payload field that marks an alert important [S1, S4]. Routes choose the escalation chain from the payload with Jinja2 templates; the first `True` wins; the documented example is `{{ payload.severity == "critical" }}` [S5]. **Binding:** the channel always sends the fixed marker `"severity": "critical"` (code, §3.2), **and** Joshua routes both the marker route and the catch-all route to an escalation chain whose notify step uses Important notifications (OA-2, OA-3). The Q7 live page proves it, because the call fires only under the Important set.
4. **Integration type: Formatted webhook** [S1]. `POST` JSON to the integration URL. Recognized fields: `alert_uid` ("A unique alert ID for grouping"), `title`, `message`, `state` (`ok` or `alerting`), `image_url`, `link_to_upstream_details`. The documented path is `/integrations/v1/formatted_webhook/<token>/`: **the URL embeds the integration token, so the whole URL is the secret.** An integration can optionally require a bearer token (`Authorization: Bearer glsa_…`, a Grafana service-account token). It is off by default; when it is on, a request without a valid token gets `403` [S1].
5. **Dedup / idempotency key = `alert_uid`.** A payload whose Grouping Id matches an **open** alert group (Firing, Acknowledged or Silenced) joins it. A resolved group accepts no new payloads; a matching payload then opens a **new** alert group [S2]. The docs do not say whether a payload joining an open group re-notifies [S2] (OQ-6).
6. **Delivery receipt.** The docs do not state the success status code or body [S1]. HTTP 2xx is provider acceptance only, never delivery (#628 card §3 item 3, `:198`). This card has no provider delivery-evidence producer; the §3.7 CLI records Joshua's operator-reported acknowledgment instead (OQ-1 RULED).
7. **Rate limits** [S3]. 300 alerts per integration and 900 per org per 5 minutes; over the limit IRM returns `429`. SMS and calls have no fixed limit, but Grafana "reserves the right to throttle or stop delivery when volume is abnormally high". Free and trial orgs have extra phone-verification limits.
8. **#628 decisions carried unchanged** (#628 card `:64-68`): C-1 read-only seam; C-2 (escalation belongs to the binding, i.e. this card); C-3 plain SHA-256 key; operator defaults OQ-1 (refusals do not notify), OQ-2 (retry with backoff until delivered, no cap) and OQ-3 (`ALL_CHANNELS_LOST` while armed is an operator-stop condition; recorded only). ## §3 — Design

1. **Kind registration.** One entry only in `book_incident_notifier.py`: `CHANNEL_KINDS["grafana_irm"] = (True, True)` (needs a secret reference; delivers). The core stays provider-agnostic and does not import the channel module.
2. **`GrafanaIRMChannel`**, in a new module `ops/c1_rail/book_incident_grafana_irm.py`, satisfies the #628 `Channel` protocol (`name`, `kind = "grafana_irm"`, `publish(idempotency_key, payload) -> PublishResult`).
   - **Body** (Formatted webhook): `alert_uid` = the idempotency key. `state` = `"alerting"` always; the rail never sends `ok`, because recovery is attended (HR §3). `severity` = `"critical"` always, a module constant with no constructor or config override (**the important marker**, §0.5 item 3). `title` = `"First Passage book incident: " + reason`. `message` = reason, `detected_at` and the first 12 hex digits of the key. No `image_url`, `link_to_upstream_details`, raw `incident_id`, account, order, strategy or figure. The body passes `assert_no_secrets`.
   - **Transport:** stdlib `urllib.request`, with no new dependency. HTTPS only, default certificate verification, **redirects never followed**, a socket timeout (each connect and read, not the whole request) strictly below `NotifierConfig.publish_timeout_s` (construction refuses otherwise), and the response read capped at 64 KiB.
   - **Acceptance mapping:**

     | Outcome | `PublishResult` |
     |---|---|
     | 2xx | `accepted`, `delivered=False`, `evidence_digest` = SHA-256 of the status code and capped body (acceptance, never delivery) |
     | 3xx (not followed); 400, 401, 403, 404, 405, 410, 413, 422 and other 4xx | `rejected` |
     | 408, 429, 5xx | `unknown` |
     | Timeout, connection, DNS or TLS failure | raise `GrafanaIRMTransportError` with no arguments, `from None` (the core journals the class name only) |

     `urllib.error.HTTPError` carries the URL (`.filename`, `.url`), so it is caught and mapped and never propagated.
3. **Secret reference.** Resolved once, at channel construction. `env:NAME` reads the process environment; a missing variable raises `NotifierConfigError` naming the reference, never a value. `secret:NAME` is refused until a store convention exists (OQ-5). The URL must be `https`, carry no userinfo, have a host ending in `.grafana.net` and have a path containing `/integrations/v1/formatted_webhook/`; a refusal names the failed rule, never the URL. The URL lives only in a private attribute: never in `repr`, `str`, exception text, `NotifierConfig.resolved()`, the digest, the journal, events or the payload. A loopback-only test allowance (`http://127.0.0.1`) is a constructor flag, off by default and unreachable from `NotifierConfig`.
4. **Config as code** (AGENTS.md `:229-238`). The instance binding is `{"name": "irm", "kind": "grafana_irm", "secret_ref": "env:FP_DMON_GRAFANA_IRM_URL"}` plus the existing `local_file` evidence channel. It lives in the Q7 driver's arguments and in tests; **no instance binding file is committed** (host wiring is out of scope).
5. **Live-page driver** (Q7 only), new `ops/c1_rail/book_incident_irm_live_page.py`. It builds a scratch `BookAccountOwner` on synthetic inputs in a directory Joshua names (for example under `local_artifacts/`), commits one `operator` halt, runs the notifier with the IRM channel from the env reference, waits, republishes once with the same key after the call step, and prints the incident key (opaque, C-3) and the journal events (times and kinds only). **Config file:** before its first publish it writes its resolved `NotifierConfig` as JSON to `notifier-config.json` in the journal's directory. `resolved()` holds references, never secret values (`book_incident_notifier.py` at MAIN `:261-268`), and `NotifierConfig.from_mapping` reads it back (`:246-259`); this file is the `--config` that OA-7 and Q7 pass to §3.7. **Imports (C1):** besides the stdlib, the notifier and the channel module, it may import `book_account_owner` and the owner-support modules its binding needs (`_validate_binding` `:457-466`, for example `BookSession` and `SettledClose`), for its scratch owner only. Its owner calls are exactly `BookAccountOwner.boot(...)` with `synthetic_broker=None` (`:374-379`; the owner has no production transport, `:348`) and then that `halt`, and #628 T9 counts both as owner mutators (test `:463`). It calls no other owner method, including `dispatch` (`:1654`), which a test asserts (U8). Apart from that admitted closure, it imports nothing on a broker, dispatch or arm path. It refuses to run without `--confirm-live-page` or with a missing reference. It labels the title `[QUALIFICATION TEST]` through a constructor argument (not config), never prints the URL and starts no background process.
6. **Retry interaction (known hazard, OQ-1).** After IRM accepts, the core writes `provider_accepted`, closes the round as accepted and keeps the job `pending` (there is no delivery evidence), with backoff 5, 10, 20, then 30 s (`book_incident_notifier.py` at MAIN `:597-610`, `:633-645`); `publish_due` re-selects it (`:505-528`; OQ-2 default). #652 (card FROZEN at `e997223`; built in #669) caps a pass at `max_jobs_per_round` jobs (NF1) in a class order (NF2, #652 card `:184-211`; `_nominate` `:530-572`). Class U is `rounds = 0 OR channels_lost = 1` (#652 §0.5 item 2, `:80-85`): every pending job never accepted by a delivering channel, plus the **lost-after-acceptance** case, a job accepted once whose latest round lost every channel. Class U sorts in three tiers (#652 §0.5 item 11 `:123-127`; NF2), each by `next_attempt_at`, then `rowid`: tier 0, the due first job of a halt sequence with no accepted page; tier 1, such a sequence's earliest-due later job while its first job is not due; tier 2, every other class-U job. Class A (`rounds > 0 AND channels_lost = 0`: accepted, still pending) follows. After IRM's acceptance the job is class A, so a pass may defer it under the owner reading OQ-NF-1 (#652 §0.5 item 7, `:106-110`: IRM already holds the alert and its own chain escalates); if a later round loses every channel, the job returns to class U. A pass that defers a due class-U job is loud (NF3, `:213-219`). While the alert group is open, each retry joins it. **Once Joshua resolves the group in IRM, the next retry opens a new group and pages him again.** The §3.7 CLI (OQ-1 RULED) closes the job first: once `record-delivery` commits `delivered`, admission finds no pending job and writes no `attempt` (J2, `:581-584`). **In-flight window:** admission commits `attempt` (`:581-588`) and only then does the publish run, outside any transaction (`:591`), so a publish admitted before the record can still POST after it; its outcome is then evidence only (J3; #628 card `:146`). A (job, channel) pair has at most one live publish (#628 card `:99`; `_refusal` `:657-658`), and its close is journaled even for a closed job: `provider_accepted` or `delivery_failed` by the round (`:597-603`); or, for a publish that outlives `publish_timeout_s`, `delivery_failed` {`timeout`} by the round (`:686-690`, `:599-600`) and `late_outcome` by the publish thread when it ends (`:677-678`, `:709-716`). These two commits race and can land in either sequence order (`:597-600` against `:674-678`, `:711`). §3.7 waits for that close (C5). **Residual:** the close ends only the rail-side window; the provider-side window stays open (§3.7 C6, OQ-6). This card does not change core semantics.
7. **`record-delivery` operator CLI** (OQ-1 RULED YES, §9; built by the D-MON-1 worker; #628 merged (P1) and this card is frozen (P3)). New `ops/c1_rail/book_incident_operator_cli.py`. Coordinator (3)'s invariant table C1-C7 (2026-10-03) is the contract: the bullets below derive from it, and U8 and U12-U15 test it. Anchors are `book_incident_notifier.py` at MAIN `d63bf32` (#628 with #669).
   - **C1 Scope and imports.** The module imports only the stdlib and `book_incident_notifier`: never `book_account_owner` and never the channel module (U8). It has no broker, dispatch, arm or owner-mutation path, and never calls `run_once`, `poll`, `publish_due` or any channel's `publish`.
   - **C2 Inputs.** `record-delivery --journal PATH --config PATH [--channel NAME] <incident_key> [--wait-s N]`. `--journal` is the notifier's journal. `--config` is the §3.5 driver's `notifier-config.json` beside it (references only), loaded with `NotifierConfig.from_mapping` (`:246-259`). `<incident_key>` is the full 64-hex key: the alert's `alert_uid`, which the driver also prints. `--channel` names the delivering channel and may be omitted only when the config has exactly one. `--wait-s` bounds the C5 wait (default 120 s; a usability bound, not a safety bound).
   - **C3 Refusals.** Each exits non-zero, names the failed check and writes no event. Items 1-5 are checked before any `IncidentNotifier` is built.
     1. The config is invalid (`NotifierConfigError`); `--channel` names no delivering channel in it; or it has more than one delivering channel and no `--channel` is given.
     2. The journal path is missing. Nothing is created (a default `rebuild=True` constructor would create it, `_connect` `:345-347`; a `rebuild=False` one raises `NotifierStoreError` instead, `:349-350`, #652 NF7).
     3. The journal is faulty, by a read-only pre-check: open `file:<path>?mode=ro` (URI) with a 5 s timeout, and require `PRAGMA integrity_check` = `ok` and `_journal_schema(db) == _JOURNAL_SCHEMA` (`:90-104`). An empty file, unreadable bytes and a hot rollback journal (which a read-only open cannot roll back) fail it. Nothing is moved aside: a default `rebuild=True` constructor would move a faulty journal aside (`:299`, `:302-303`; `_move_aside` `:380-398`), and beside a running notifier that re-owes and re-pages every committed incident (#628 card `:86-90`). The pre-check stays as an early refusal. **Race closed in the constructor:** the pre-check and the constructor's own `_journal_fault` (`:358-378`) are separate opens, so the CLI constructs with `rebuild=False` (C4; #652 NF7, P5). A journal that goes missing or turns faulty between them then makes the constructor raise `NotifierStoreError` (`:300-301`, `:349-350`), creating nothing, moving nothing aside and writing no `journal_rebuilt` event (instead of `:302-310`); the CLI exits non-zero as in item 6. An empty or table-less file is not a `_journal_fault` fault (`:361`, `:378`), but under `rebuild=False` the constructor's schema check refuses it with `NotifierStoreError` and initializes nothing (`:305-306`; #652 §0.5 item 6, NF7). A hot rollback journal is not a fault either; the constructor rolls it back like any notifier open (`:370`). Neither is moved aside. *As drafted (superseded by #652 §0.5 item 6):* the constructor initialized an empty file as a fresh journal.
     4. The key is unknown: not 64 lowercase hex, or no `jobs` row (`record_delivery` would raise the same, `:734-735`).
     5. The key has no `attempt` event on that channel in the journal, so no page went out on it. The CLI must check this itself: `record_delivery` checks the channel against the config only (`:728-729`).
     6. The journal lock stays busy past 5 s. `_journal` opens with `timeout=5` and `BEGIN IMMEDIATE` (`_connect` `:347`, `:349-350`; `_journal` `:329`), so the constructor's or `record_delivery`'s transaction raises `NotifierStoreError` and rolls back.
   - **C4 Record.** The CLI builds an `IncidentNotifier` with `rebuild=False` (C3 item 3; #652 NF7) and one inert, non-publishing object per channel spec, carrying the spec's name and kind (the constructor checks both, `:283-286`, which is why `CHANNEL_KINDS["grafana_irm"]` is needed), and a `read_incidents` it never calls. It calls `record_delivery(key, channel, digest)` once (`:723-737`). The digest is SHA-256 over a domain-separated record of the key, the channel and the local recording time, labelled operator-reported acknowledgment; it is not authenticated attendance (TB-I3, HR `:143`). Afterwards the key has exactly one `delivered` event. **Idempotent:** on a job already `delivered`, `_transition` writes nothing (J5; `:627-628`, `:736-737`), so a re-run writes nothing, prints `already delivered` (the job's `delivered` event does not carry this run's digest) and goes on to C5; it exits 0 once C5 passes. **Second writer:** every journal access is a fresh connection with `BEGIN IMMEDIATE` (`:323-339`), and `_transition` updates only `AND state='pending'` (`:642-645`), so the record is serialized with a running notifier and cannot regress a job. `_round_lock` holds within one process only (`:297`); the CLI runs no rounds. No #628 test runs a second process on one journal, so U13 tests it; if #628's journal fails U13, return NEEDS_CONTEXT.
   - **C5 Safe check (rail side).** After the record, the CLI polls the journal read-only (the C3 open) for the events of (key, channel) in sequence order and takes the last `attempt`. J2 admits no `attempt` after `delivered` (`:581-584`), so no new attempt can start once the record is written and that attempt is final. It waits, bounded by `--wait-s`, until that attempt has a later **close**: `provider_accepted`; `delivery_failed` with an outcome other than `timeout`; or `late_outcome`. `delivery_failed` {`timeout`} is **not** a close: the abandoned publish may still be running, and it closes as `late_outcome` (`:686-690`, `:713-716`), which may be journaled before or after the `delivery_failed` {`timeout`} row. Either order is fine: C5 needs only a close event after the last `attempt`. With one live publish per pair (`:657-658`), a close after the last attempt is that attempt's. It then prints `safe to resolve (rail side)` and exits 0. If the wait expires, it prints `not safe; wait and re-run` and exits non-zero, and Joshua leaves the group acknowledged. The check is never a clock bound: the transport timeout bounds each socket operation, not the whole request, and an attempt's `at` is its round's start (`:515`, `:586`). **Preconditions:** there is one `IncidentNotifier` instance per journal, a host-wiring precondition (the one-live-publish rule is per instance: `_publishes` `:298`, `:655-658`). Each poll also requires the job state `delivered`, so a journal rebuilt at the same path is not read as safe. A poll read error counts as not safe. **Fail safe:** if `late_outcome` never appears (`_record_late` swallowed a journal error, `:720-721`, or the notifier exited with the publish live, or the round-close write failed with `NotifierStoreError` at `:597`), the CLI reports not safe on every run, and that key stays acknowledged-only and is never resolved.
   - **C6 Residual (provider side).** C5 closes only the rail-side window. A close marks the end of the rail's request, not of IRM's processing. A POST that IRM received but whose response was lost (a transport failure, which the rail closes as `delivery_failed` within `publish_timeout_s` and as `late_outcome` past it), or one answered `408`/`429`/`5xx`, can still be grouped after the resolve and open a new group. A 2xx is acceptance only (§0.5 item 6), so grouping may also complete after it. The provider side is watched for at Q7 (OQ-6), but a clean Q7 does not close it: Q7 cannot provoke a lost-response POST, because the driver has exited before `record-delivery` runs. OQ-6 stays OPEN. The rail never sends a resolve (`state` is always `alerting`, §3.2). Joshua may add a wait before resolving; it narrows the window and is not a guarantee.
   - **C7 No other effect.** No HTTP request, no secret resolution (the CLI never imports the channel module, so no `env:` reference is read) and no owner write (U12).
   - **Operating sequence:** acknowledge in IRM → `record-delivery` with the driver's config file → wait for `safe to resolve (rail side)` → resolve in IRM (OA-7, §6.3).
