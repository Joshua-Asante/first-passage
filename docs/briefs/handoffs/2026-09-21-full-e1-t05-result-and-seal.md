## 0.5. Frozen decisions (constraints, not options)

**F1 — File boundary (amendment §T05).** T05 owns only new modules and new versioned tables. Every touch point into S3/S4/S5-owned files is a named **integration seam**: a one-line registration or dispatch hook that calls a T05 function with a signature fixed in §1. The executor delivers the functions and a seam table (§7); the coordinator applies the seams at acceptance after T04. Until then, T05's tests exercise its modules through its own fixtures and a service double that supplies the real `threading.Lock` semantics and the real `CampaignStore` on a DB whose `user_version` is the T05 test layout (§1, "custody").

**F2 — Custody.** New versioned tables `full_campaign_result_*` and `full_campaign_seal_*` in the same SQLite journal, created by T05's own schema strings and validated by exact layout, mounted at DB `user_version` **9** = the S3 v8 layout + RESULT_SCHEMA + SEAL_SCHEMA (the seam adds the version branch in `store.py` exactly as S3 added v8). One closed family per slice: `qualification_campaign_result/v1`, `…_result_authentication/v1`, `…_result_receipt/v1`; `qualification_campaign_seal_intent/v1`, `…_seal/v1`, `…_seal_receipt/v1`. Bytes of these families live only in the new tables.

**F3 — Progression names (frozen here for S4/S5 too).** Terminal statistical predecessors a result commit may consume: `N1_FAILED` (S3), `N2_FAILED` (S4, the joint N2/PART_B failure), `PART_A_FAILED` and `FULL_PASS_READY` (S5). Outcomes: `RESULT_COMMITTED_FAIL`, `RESULT_COMMITTED_PASS`, then `SEALED_PASS`. Any other predecessor state refuses (`CONTINUE`-only prefixes, `IN_DOUBT`, `BUDGET_UNCERTAIN`, VOID). The coordinator carries these names into the S4/S5 packets.

**F4 — Isolated charged processes (spec §2.5, D2 pattern).** The result-aggregate G5 runs as a host transient unit under the campaign's work slice, launched by the guardian exactly as `_run_n1_g5` launches the N1 G5, under manifest role `result_g5` charged to the `RESULT` reservation. qseal runs as a **separate** host transient unit (`User=` the seal principal, its own credential root, no Docker/worker/result-key access) under manifest role `seal`, charged to the `SEAL` reservation, with `RuntimeMaxUSec`/CPU bounds derived from that phase. Neither is an in-process mock; on Windows their bodies are exercised as functions, and the unit launch is Linux evidence at acceptance.

**F5 — Signing recovery mirrors S3.** Fixed payload, key id, signing instant and intent identity are persisted (T1) before any signature; the commit (T2) is one transaction under `dispatch_lock`; an exact retry returns the byte-identical receipt with `historical=true` and the current validity; a different candidate under a persisted intent always refuses; no fresh time, key or payload on retry.

## 3. Behavior (binding; from S6/S7 and spec §2.8)
- Result: G5 constructs the aggregate from retained captures/assessments read through the bounded client; the service reserves `RESULT` **before** taking the result snapshot; in one serialized transaction it rechecks snapshot/revision, membership, VALID, current approvals/keys and budget, then publishes result/authentication/artifact membership and one receipt together; the receipt binds the resulting journal head and the budget settlement. Fresh signing/validation retries are charged; saved-receipt retries are historical reads. A statistical FAIL commits as evidence and is never sealed. Operational abort/uncertainty stays incomplete — never a fabricated FAIL.
- Seal: only `RESULT_COMMITTED_PASS` with all five decisions PASS reaches qseal. The service takes the same lock as VOID, verifies current PASS, exact receipt, current approvals/keys and `SEAL` budget, prepares the durable intent, calls qseal over bounded private IPC, rechecks validity/budget immediately before publication, and publishes seal bytes + receipt atomically. qseal validates independently; it cannot publish. A later VOID preserves history and revokes current usability. FAIL, incomplete, uncommitted, uncertain, exhausted or VOID campaigns never gain a new seal.
- Both slices: crash before T1 → nothing to recover, historical inspection only; between T1/T2 → exact retry completes with the persisted instant; after T2 → byte-identical receipt, `historical=true`; response lost → same. VOID-first → commit refuses; commit-first → later VOID flips validity only.

- [ ] S6: genuine all-stage PASS and each legal early-FAIL aggregate (from the synthetic-predecessor fixtures) commit; missing/extra/out-of-order stages and successful incomplete prefixes refuse; private staging + exact intent + candidate retention under the original allowance; both VOID orderings with barriers; lost response after commit; expired/revoked key before commit; `RESULT` exhaustion; one immutable receipt with truthful validity wrappers.
- [ ] S7: PASS-only eligibility; wrong role/result/domain; altered intent; expired/revoked seal key; lost signing response; both VOID orderings; no alternate candidate publication path; exact receipt recovery after later VOID/expiry; a signing failure rolls back publication, not the intent.
