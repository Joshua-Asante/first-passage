- **(A) Gap 1 — kernel-bounded payload CPU.** cgroup v2 has no cumulative CPU cap, so the bound is *rate × wall*, both enforced by the kernel/system manager independently of the guardian's Python. Default: set `CPUQuotaPerSecUSec` (systemd resource-control; realizes as `cpu.max`) on the **payload slice** in `guardian_unit_spec`'s `payload` properties, with quota `Q = floor(budget_cpu_ns / T_ns × 10^6)` µs per second where `budget_cpu_ns = limits.cpu_ns − orchestration_cpu_ns[phase]` (the same `budget_cpu` as `_run_probe` :864) and `T_ns = remaining_wall_ns` (the value already used for the guardian's `RuntimeMaxUSec`). Then cumulative payload CPU ≤ Q × RuntimeMax ≤ budget regardless of guardian liveness, because `RuntimeMaxUSec` is enforced by the manager (SIGKILL, `KillMode=control-group`) and `BindsTo` retires the payload slice with the guardian. Derive both from existing limits; add no profile constant. Verify the realized `cpu.max` on the payload slice after start (fail closed, as `LinuxCampaignRuntime.__init__` does for memory). Keep the `_run_probe` poll as the early-stop/accounting path, not the enforcement. Consequence the coordinator accepts for the diagnostic profile: the payload is rate-limited to `cpu_ns/wall_ns` of one CPU (33 % for 100 s/300 s); the `descendants` case will run to ~the wall deadline; the phase ratio is a later profile decision, not this repair's.
