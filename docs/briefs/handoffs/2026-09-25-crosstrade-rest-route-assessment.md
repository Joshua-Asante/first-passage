### 6.2 Request scope (step 1)

- **Route.** CrossTrade `/v1/api/tv` runs server-side against the linked Tradovate identity. This is CrossTrade-mediated REST, not direct Tradovate API eligibility (T08 §7.4's exclusion is unaffected). It needs the Pro plan; entitlement is vendor-reported, not checked (Q01).
- **Ordinary bracket placement.** `POST …/orders/place` with absolute `stopLoss` (and optional `takeProfit`) is one Tradovate `placeOSO`. The response carries the entry `orderId` plus child ids `oso1Id`/`oso2Id`/`osoChildIds` (Q02). The exits are GTC and their prices are fixed at submission, never recomputed from the fill. Tradovate activates them on the entry's **first fill, sized to that fill** (Q14, Q19). This is the same broker primitive as the webhook `take_profit`/`stop_loss` path.
- **Correlation.** `orderId` (the caller's tracking id, remembered 7 days) is forwarded as `clOrdId`. Tradovate accepts a repeated `clOrdId`, so it is a **label, not an idempotency key** (Q05, Q07).
- **Excluded shapes.** Inline `atm*` fields return an `orderStrategyId` with no child map. They carry no broker `clOrdId` and fall outside the reconciliation recipe (Q02, Q20). Their managed layer has a 24-hour watcher and durable trigger replay (Q12, Q30), which is exactly the deferred-work class to keep out. REST has no `delay=` field. `cancel_after` exists and schedules a second mutation (execution-internals command table, near Q17).
- **Hidden account configuration** can add actors that no request-level narrowing removes. The same controls as webhooks apply (Q01):
  - a Trade Copier where this account is **leader** fans REST placements out to followers (Q11);
  - a copier where this account is a **follower** in execution or order mode injects foreign orders and fills regardless of source (Q26);
  - Account Manager auto-close, scheduled or window flatten, Block Signals and Closing Only can close positions or refuse requests (Q27).

  None of these was inspected (no account access). They are CAP R5 inventory, still UNPROVEN.

### 6.4 Correlation and recovery (step 3)

- **Positive path (same session).** Carry the intent id as `clOrdId`, then:
  1. list working orders and all session orders (Q07);
  2. read each candidate's lifecycle, where the `New` command carries the `clOrdId` (Q20);
  3. read fill-reconciled positions.

  A match gives `orderId`, then `ocoId`/`parentId`/`linkedId` for the children and `ordStatus` (Q20), then fills by `orderId`. This supplies the owner's needed fields: a correlated `operation_id` for `BrokerFact` (unknown `operation_id` halts, `book_account_owner.py:1922-1926`), fill quantity and price, and a terminal status. **Correlation, not uniqueness**: a repeated `clOrdId` is accepted (Q05). Uniqueness is our own discipline (one `clOrdId` per attempt, never reused), and a duplicate match must quarantine, per the closure-plan collision row.
- **Negative inference (rejected).** The recipe's last step is to place again when no order carries the id (Q08). Nothing documented proves that an absent match cannot appear later:
  - there is no vendor processing bound (support: no time bound; processing continues after disconnect);
  - order lists are session-scoped and reset about 17:00 ET (Q10, Q22);
  - fill history is periodic, has no `clOrdId`, and its end-of-list is "not verified capture completeness" (Q23, Q24);
  - the WebSocket stream drops frames with no replay (Q25).

  We do not adopt resend-on-absence, consistent with CAP 09-17 (`capability-decision.md:107-115`).
- **Pending original processing vs identified terminal order.** An identified order with a terminal `ordStatus` resolves *that order*. It does not close the request if work is still possible elsewhere: sibling children, CrossTrade coverage repair on a watched bracket (Q15), or copier fan-out (Q11).
- **Session boundary (reconciled 2026-09-26).** The documented candidate lists are session-scoped (Q22), and history rows lack clOrdId. This limits the documented correlation recipe; it does not prove that every unresolved request becomes unknowable forever. **Cross-session recovery is not established; preserve the unknown state until qualifying evidence resolves it.** A later fill whose orderId cannot be attributed remains an unexplained effect under incident ADR §A2 rule 6. Retain any learned identities and evidence; D5 must test prior-session lifecycle access separately. Session reset is neither a no-future-effect fence nor permission to release reservations or resend. Current blocking rules continue while the request is unresolved; any Proposed-B treatment requires separate acceptance.
- **Unknown cancel, change or close.**
  - `change` is Tradovate modify. A version can exist for a command Tradovate later rejects, so resolution is by command report (Q21). Whether the old stop survives a rejected or unknown modify is **undocumented** (L2(c) stays K).
  - `cancelreplace` is guarded and non-atomic but owner-fenced, and returns `reconciliation_required` on ambiguity (Q28).
  - Full `close` is `liquidateposition`, a request rather than a guarantee (L2(d) K per §A4).
  - Partial close is an opposing market order that leaves working orders in place (execution-internals command table; §A4 U).
