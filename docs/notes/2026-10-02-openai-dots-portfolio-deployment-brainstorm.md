## Documented capabilities and access limits

OpenAI describes dots as agents that continue work between conversations, with their own cloud computer and browser. Account access is rolling out gradually; this session has not verified Joshua's access. [Meet dots](https://learn.chatgpt.com/docs/dots)

A dot can coordinate new cloud coding tasks in a configured Codex environment and continue identified local Codex tasks. New tasks receive selected instructions and context rather than every prior conversation. Fixed recurring work needs a saved schedule; supported service events can trigger monitoring, but an app connection alone creates no monitor. Memory is useful context rather than a complete transcript. [Tasks and memory](https://learn.chatgpt.com/docs/dots/tasks-and-memory)

Local work requires a separately connected computer, online with the ChatGPT app open. The cloud browser has its own sessions. Plugins and local skills depend on account permissions and the execution environment. Connecting Codex or Work Sync alone does not grant a dot local access. [Computers and apps](https://learn.chatgpt.com/docs/dots/computers-and-apps)

Custom rules can constrain actions alongside product safeguards and review. Pausing the main dot task does not stop all delegated tasks or cancel schedules; those need separate controls. Product controls should complement the project's authority contracts, and are not evidence that a trading interlock is satisfied. [Controls](https://learn.chatgpt.com/docs/dots/controls)

## Adoption choices

**Advisory coverage across all three areas.** Start with source-linked blocker changes, decision drafts, engineering return summaries and session preparation. Lowest setup burden and easiest to assess; Joshua or the coordinator still performs routing. This is the recommended first experiment.

**Routing approved work.** Add permission to create or continue identified Codex tasks against committed cards and relay returns to named recipients. This can remove repeated dispatch effort, but requires proven task access, context transfer, concurrency limits and a clear single writer for shared files. Delegate implementation through bounded handoffs; retain combined acceptance with the coordinator.

**Broader orchestration.** Consider responsibility for the cross-workstream flow, including evidence collection and authorized attended assistance. Greatest potential attention savings, with greater risk of stale authority, duplicate work and blurred ownership. Any coordinator-seat transfer needs its own recorded handoff. Keep time-critical trading and protection in their approved deterministic services.

These are levels of responsibility for one initial dot, not a recommendation to create three competing coordinators. The existing heartbeat already covers part of the continuity problem. Measure the added value before replacing it or adding another monitor. Human SEND or operator-act requirements remain in force wherever the current card requires them; agent account actions remain possible only under the operator's applicable direction and session gates.

## Proposed first experiment and verification

Propose one bounded advisory cycle covering an engineering return, an operator decision and an attended-session preparation packet. First verify dot availability, necessary task and repository access, notification destination, and the allowed public versus private evidence surface. Local private book sources retain the primary-checkout read restrictions in AGENTS; do not copy or upload them into cloud tasks. Keep private account evidence out of this public note.

The coordinator supplies the current owner links and exact task IDs. The dot returns one concise packet: what changed, evidence identity, what remains unresolved, next authorized action, who decides and when it should next check. Notify on a meaningful change, failure, conflict or needed decision; stay quiet when nothing actionable changed. Fixed periodic monitoring would need a separately saved and confirmed schedule, not an assumption about autonomous wakeups.

Evaluate whether the cycle reduced Joshua's context gathering and repeated instructions. Acceptance should include correct source identities, no duplicate assignments or relays, no readiness claim beyond its evidence, and an explicit return to the coordinator. Exercise a changed head, an offline local computer, an ambiguous vendor reply and a stop request; verify that stopping covers delegated work and schedules separately. Do not assume cloud availability meets operational freshness or escalation timing.

Only after that result should Joshua choose additional routing or session privileges. A custom MCP or dashboard is an optional later investment if existing connections cannot provide reliable reads; it is unnecessary for the initial documentary experiment. Usage, connection availability and maintenance burden need measurement before assigning a permanent budget.
