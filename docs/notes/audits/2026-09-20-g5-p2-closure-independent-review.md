## Findings

**BLOCKING — none.**

**ADVISORY-1 (lens 1f) — the contract anchor is an un-chained retained row, so the tamper class P2-1 described has a one-step sibling.** Scenario (reproduced on the branch): credit an enrolled work with a real payload identity, then delete `supervision_<work>` alongside the PROCESS rows → reopen clean, credit intact, on a funded attempt with an enrolled admission. Equivalently, a store-direct caller that never enrolls credits freely (the `persist` scene). R1 explicitly scopes un-enrolled works out of the rule, so this is not a departure from the ruling; it is a residual the coordinator should record against A5/S3 rather than treat as closed. Candidate tamper-evident anchors if a later packet wants one: the work's START_INTENT `data.work_scope_id`/`campaign_scope_id`, which sit inside the chained budget state and equal the enrollment's `payload_slice`/`campaign_slice` on both launch paths (`campaign_supervisor.py:110-113`, `campaign_funding.py:704-710`) — the walk could refuse an enrollment whose slices disagree with the chained START_INTENT and, on a funded profile, a credited non-admission work whose chained scope is slice-shaped but has no enrollment; the Windows `persist` scene would then need an honest non-slice scope. Not authorized by G5; no change requested here.

**ADVISORY-2 (lens 2/3) — "every historical journal reopens" is proven for the parser, not for R1's walk against real pre-G1 journals.** Enrollment and PROCESS retention arrived together (`292f283`), but until G1 the guardian credited on `ExitCode==0` without checking that any pid had been observed (`f2606b0:911-925`; `seen_pids` unused for credit). A real journal from a pre-G1 S2 run in which a short-lived payload exited before the first poll would hold an enrolled COMPLETED work with zero payload-scope PROCESS rows and would be refused by the branch's walk — as it would already have been by G4's presence-scoped walk (the guardian's own PROCESS row engages it). That refusal is arguably correct under R1 (it is the very defect G1 fixed) and no tooling reopens downloaded journals through `CampaignStore` (`s2_run_evidence.py` and `campaign_host.py` read raw sqlite), so the practical exposure is nil; but the §7/ledger sentence should be scoped to "parses" or backed by the real predecessor fixture the packet preferred. Test 3 cannot detect this because it constructs the journal on the branch's own store.

**NOTE-1 (lens 2) — the store still accepts new v1 writes.** `retain_supervision_event` stores any version the parser accepts; "nothing new is written in v1" is a producer property (true: all twelve producers emit v2) and not a store refusal. This is what lets the compatibility tests write v1 rows through the API; no change wanted, just the precise reading.

**NOTE-2 (lens 3) — fail-on-base for test 2 is helper-confounded without a shim.** Against untouched base production the test fails on `AttributeError: SUPERVISION_EVENT_V2` from `_retained_process_event` before reaching the property. With the constant routed to v1 it fails on the property (`DID NOT RAISE` at :1056). The executor's §7 reports test 1 and test 3 as the fail-on-base pair, which is accurate; recording that test 2's base failure is incidental avoids a false "evidence of the property" reading later.

**NOTE-3 (R3) — label corrections verified.** G3 §7 and G4 §7 carry the bracketed corrections; `e85f96c` is an ancestor of the branch head and `tools/qualification_verification/README.md:196-201` carries its polkit trust-model text, so A9-4 = closed is correct and GLM's "open" label was wrong. The packet's own §2.4 rejection list (DEADLINE/PROCESS_UNOBSERVED under v1) was the error the executor corrected, and the ledger records the acceptance.

**NOTE-4 (out of scope of the two P2s) — the Linux 14/15 is not a G5 regression on this evidence.** The G5 diff does not touch the resume handshake, the re-send window, the probe or the OOM case; the failing node's identity-bearing path is the one the addendum in lens 5 targets.
