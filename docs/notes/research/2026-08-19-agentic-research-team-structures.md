# Agentic Research Team Structures — Applicability to First Passage's Front Office

> **(Retired 2026-08-31 — see [docs/adr/2026-08-31-persona-hierarchy-full-retirement.md](../../adr/2026-08-31-persona-hierarchy-full-retirement.md).)** This note's applicability analysis (authored 2026-08-19) treats the persona-hierarchy review panel described below as a live, currently-operating system. It has since been fully retired: no persona (CIO, Head of Research, Falsifier/Pre-Registration Analyst, or any other seat named below, including in the Addendum) is spawnable, and every `docs/personas/` file this note cites or quotes from (design spec included) has been deleted. The analysis stands as an accurate historical record of reasoning made while the panel existed; every present-tense reference below to "the existing panel," "the persona hierarchy," or a named seat's "own file" describes 2026-08-19 repo state, not current state.

## Purpose and scope

First Passage already runs an independent **review/audit** persona hierarchy (CIO → Head of Research → Falsifier Analyst / Pre-Registration Analyst) that fires on GRAND-tier ratifications and strict-D2 STRATEGIC-tier Deletes, spawned fresh per review with no visibility into the generating session's live reasoning — a design explicitly borrowed from SEC 18f-4 / SR 11-7 model-risk-management independence framing, naming a "Kerviel/Adoboli-shaped" reviewer-converges-with-generator failure as its threat model. The actual strategy-*discovery* work (a3: MNQ mining against the TNEC-1 intake gate; a4: harvest/external-mechanism intake) is **not** organized this way today — it runs as ad hoc operator-driven Claude Code sessions and skills, with no defined roles or division of labor. This note answers: **should a3/a4 be organized as a structured agentic generation team, and if so, how should it interface with the existing audit panel without collapsing the panel's independence guarantee** — given three hard constraints (no new infrastructure beyond Claude Code Agent/subagent spawns and the existing Workflow orchestration tool; no backdoor around the K-budget/pre-registration discipline; no incentive for generator/reviewer convergence). It synthesizes five parallel research sweeps into applicability verdicts against this specific seam question, not a general literature summary.

## Methodology

Five parallel web-research sweeps (WebSearch/WebFetch, prioritizing 2024–2026 sources):
1. **Anthropic's own published multi-agent research system** — orchestrator/subagent design, context-engineering primitives, Claude Code subagent mechanics.
2. **Production OSS multi-agent frameworks** — CrewAI, MetaGPT, AutoGen, LangGraph — plus Cognition's counter-position and a self-attribution-bias paper.
3. **Quant/finance research-desk org models** — hedge-fund pod structures, SR 11-7 / 18f-4 / Three-Lines-of-Defense independence frameworks, live AI-augmented fund examples (Man Group, QuantConnect, Microsoft RD-Agent(Q), institutional roundups).
4. **Academic multi-agent-debate and LLM-as-judge literature** — the founding multi-agent-debate result and its 2025–2026 walk-backs, debate-hacking/sycophancy failure mechanisms, judge-reliability and self-preference-bias studies.
5. **Agentic-team failure modes and anti-patterns** — taxonomy studies (MAST), correlated-error/monoculture findings, verification-theater and evaluator-gaming critiques, deliberately adversarial to the premise of adding any team structure at all.

A revision pass re-verified several disputed citations directly against primary sources (paper abstracts, the Anthropic blog post, the Apple study, CrewAI's own docs vs. community reporting) and cross-checked two candidate-option claims against this repo's actual K-ledger code (`lab/discovery/register_search.py`, `lab/research_utils/axis_screen.py`) and its governing ADRs. Corrections and additions from that pass are marked inline where they change a claim from the prior draft.

## Findings by angle

### Angle 1 — Anthropic's own multi-agent research system

- **Orchestrator spawns pre-scoped, non-overlapping subagents; documented duplicated-work failure from vague delegation.** *Applicable* — this is the load-bearing precedent for a3/a4 fan-out, buildable today with existing primitives; the documented failure (two subagents independently re-investigating the same question) is the concrete argument for partitioning mechanism/instrument cells *before* spawn and routing K-ledger updates centrally. [Anthropic Engineering — multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- **Context isolation ("isolate" as one of four context-engineering moves): subagent explores in a clean context, returns only a condensed summary.** *Applicable* — validates that the existing review panel's fresh-spawn design is not a bespoke invention but Anthropic's own primitive; usable identically for a3/a4 generation subagents. [Anthropic Engineering — effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- **Claude Code subagents carry a "sibling roster" of other agents active in the same parent session.** *Applicable and load-bearing* — running a3/a4 generation subagents and panel-reviewer subagents as siblings under one parent Workflow run could leak the generator's identity into the reviewer's spawn context (and vice versa), a subtle collapse of independence; the panel must be invoked as its own top-level run against the frozen artifact, never as a sibling branch. [Claude Code docs — sub-agents](https://code.claude.com/docs/en/sub-agents)
- **Evaluator-optimizer pattern (generator + evaluator iterate in a feedback loop).** *Applicable as a negative precedent* — this is structurally the same shape as the reviewer-converges-with-generator failure the ADR names; explicitly the pattern to avoid at the generator↔panel seam. [Anthropic Engineering — building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- **Parallelization vs. orchestrator-workers taxonomy.** *Applicable* — a3 (fixed TNEC-1 search space) fits pre-partitioned parallelization; a4 (adaptive literature harvest) fits orchestrator-workers, which is harder to pre-register cleanly and needs an explicit rule for when new sub-tasks spawn mid-campaign so K accounting doesn't silently grow. [Anthropic Engineering — building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- **Published token-cost figures for these architectures vs. a plain chat interaction.** *Applicable, cited precisely here because a later section of this note previously misstated it* — Anthropic's own published numbers are two distinct comparisons, both measured against a single chat interaction, not against each other: "agents typically use about 4× more tokens than chat interactions," and its multi-agent research system "use[s] about 15× more tokens than chats." Neither figure is a per-campaign cost for a3/a4's specific shape — no source measures that — so the honest transfer is "meaningfully more expensive per unit of work," not a specific multiplier claimed for this repo. See Candidate B below, where this correction is applied. [Anthropic Engineering — multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- **Stateful failure handling, checkpoints, rainbow deployments.** *Not applicable* — this is production-service engineering for a continuously-running multi-tenant system; First Passage's campaigns are bounded, operator-driven sessions, and constraint #1 rules out standing infrastructure regardless.

### Angle 2 — Production OSS multi-agent frameworks

- **CrewAI role/goal/task-context split; Hierarchical mode's "manager validates results before proceeding."** *Mixed* — the role/task-context primitive maps cleanly onto Agent/Workflow for a3/a4's internal division of labor; but "manager validates its own workers' results" is structurally the rubber-stamp risk the ADR guards against and must not be reused for the generator↔panel interface. [CrewAI docs — Processes](https://docs.crewai.com/en/concepts/processes)
- **CrewAI `max_iter` cost-blowup risk — re-attributed.** *Applicable as a concrete K-budget-backdoor illustration, but the "5–10×" figure is community-reported, not CrewAI's own documented claim, and the prior draft's attribution was wrong.* CrewAI's own Processes docs describe the hierarchical-manager mechanism but state no cost multiplier; `max_iter` defaults to 25 and is uncapped by default, and third-party production writeups and CrewAI's own community forum describe retry loops and re-processed shared context producing 5–10× (one anecdote: overnight $2,400 from a single stuck crew) token-cost blowups. Treat this as a community-observed operational failure mode, useful as an illustration of what "generators self-report K without a hard ceiling" looks like in practice — not as an officially documented CrewAI figure. [CrewAI docs — Processes](https://docs.crewai.com/en/concepts/processes) · [CrewAI Community — token spend as a CI cost gate](https://community.crewai.com/t/field-note-treating-your-agents-token-spend-like-a-ci-cost-gate/7725) · [DEV Community — How to Stop AI Agent Cost Blowups Before They Happen](https://dev.to/sapph1re/how-to-stop-ai-agent-cost-blowups-before-they-happen-1ehp)
- **MetaGPT: structured document artifacts over a pub/sub message pool, not free-form chat.** *Applicable* — matches and validates the repo's existing discipline of frozen artifacts / pre-registration manifests over conversational trace; pub/sub role-filtering is a legitimate way to scope what each a3/a4 sub-role sees without full context sharing. [MetaGPT paper](https://arxiv.org/html/2308.00352v6)
- **AutoGen Swarm/GroupChat: full shared message history across all participants by design.** *Applicable as a clear negative precedent* — architecturally the opposite of the independence the panel needs; usable only for generation-internal coordination, never for generator→panel handoff. Documented infinite-loop/over-invocation bugs argue for a hard round cap wired into the K-ledger. [AutoGen docs — Swarm](https://microsoft.github.io/autogen/stable//user-guide/agentchat-user-guide/swarm.html)
- **LangGraph: handoffs carry a selectable context scope (`full_history` vs. `last_message`).** *Most directly transferable primitive* — the Workflow tool can implement the same firewall: the panel side always uses the equivalent of zero-history (artifact-path only), never `full_history`. The maintainers' own advice to hand-roll this on tools rather than adopt the framework also supports building directly on existing primitives. [langgraph-supervisor-py](https://github.com/langchain-ai/langgraph-supervisor-py)
- **Cognition: "Don't Build Multi-Agents" — parallel subagents without shared context silently diverge on implicit decisions.** *Applicable but scoped narrowly* — a real caution against fragmenting one trading-mechanism hypothesis across subagents that can't see each other's assumptions (generation-side coordination), **not** an argument against the panel's deliberately opposite, isolation-heavy design. [Cognition — Don't Build Multi-Agents](https://cognition.com/blog/dont-build-multi-agents)
- **Self-attribution bias — corrected reading.** *Corrected in this revision; the prior draft's claim was inverted relative to the paper's actual mechanism.* The paper ("Self-Attribution Bias: When AI Monitors Go Easy on Themselves") finds AI monitors rate actions more favorably when those actions appear to originate from the model itself — but the driver it identifies is **conversational turn framing**, not shared weights or persona lineage: bias appears specifically when "the action is presented in a previous or in the same assistant turn instead of being presented by the user in a user turn," and the paper explicitly states "explicitly stating that the action comes from the monitor does not by itself induce self-attribution bias." *Applicable, but in the opposite direction from the prior draft* — this is actually evidence **for** the panel's existing design, not a warning against it: a fresh-spawn reviewer reading a frozen artifact is structurally a fresh user turn, never a continuation of the generating session's own assistant turn, and so sidesteps the exact mechanism this paper identifies. It does **not** support a claim about persona lineage or shared-weights correlation — that concern is real, but the right citations for it are CAPA and the Apple panel-correlation finding below (Angle 3 and Angle 5), not this paper. The note's prior recommendation to "differentiate panel-persona prompts/lineage from generator-persona prompts/lineage" is retained in the cross-cutting synthesis, but is now grounded in those two sources instead. [Self-Attribution Bias, arXiv:2603.04582](https://arxiv.org/html/2603.04582v1)

### Angle 3 — Quant/finance research-desk org models

- **Multi-manager pod structure: PM + analysts, reporting into a centralized, always-on risk desk that can force de-risking regardless of pod conviction.** *Applicable* — a small generation "pod" (idea-generator + implementer) reporting into a centrally-owned constraint layer (already `dd_protection`/K-budget) is the natural generation-side shape; the pod's own risk desk is an always-on constraint analogue, **not** the periodic-independent-review analogue the panel already fills. [Peakframeworks — hedge fund pods](https://www.peakframeworks.com/post/who-are-the-major-hedge-fund-pods)
- **Young & Calculated: quant-fund signal funnel — hypothesis-sourced ideation (behavioral, structural, information-processing), then a seven-stage vetting sequence (in-sample → out-of-sample → capacity → decay → correlation → regime-stability → paper-trading) before live capital, at firms reportedly running millions of evaluated candidates down to a much smaller deployed set.** *Weakly applicable* — this describes human quant-team practice (WorldQuant-scale), not an agentic team, and says nothing about AI agents, roles, or independence, so it does not bear on the seam question directly. Its usable content is generic vetting-funnel vocabulary a3/a4 could borrow stage names from (e.g., naming a4's own funnel "hypothesis source → in-sample → OOS" explicitly), and its explicit warning that "pure data mining without a hypothesis produces signals that fail in live trading because the relationships found are statistical artifacts rather than causal mechanisms" reinforces — without adding anything new to — this repo's existing pre-registration-before-scoring discipline. [Young & Calculated — How Quant Hedge Funds Actually Build and Vet Trading Signals](https://youngandcalculated.substack.com/p/how-quant-hedge-funds-actually-build)
- **SR 11-7 / SEC 18f-4 independence framing (already cited in the repo's own ADR).** *Applicable, partial analogy* — confirms the borrow is correct-in-spirit (spawned-fresh, artifact-only mirrors "no stake in whether a model is valid"), but SR 11-7's independence is anchored in organizational facts (distinct reporting line, compensation not tied to outcome) a persona spawn cannot literally have; 18f-4 governs an always-on constraint function (closer to the pod risk desk), not a periodic ratification review — conflating the two independence needs risks over- or under-protecting one. **This gap has a sharper edge than stated here — see the dedicated solo-operator discussion in Cross-cutting synthesis below.** [SR 11-7](https://www.federalreserve.gov/boarddocs/srletters/2011/sr1107.pdf) · [18f-4](https://www.dfinsolutions.com/knowledge-hub/blog/sec-rule-18f-4)
- **Three Lines of Defense: 1st line (owners/generators), 2nd line (independent validation, reports to CRO), 3rd line (audit of the first two, reports to the board).** *Applicable* — gives a cleaner 3-tier vocabulary than the current 2-tier framing and surfaces a real gap: there is no 3rd-line-equivalent auditing the panel's own review process (the repo's own ADR self-review found real code defects post-hoc, which is 3rd-line-shaped work done ad hoc, not by design). This generic explainer is retained for its clean vocabulary, but see the next finding for the more targeted, AI-specific version of the same model. [MetricStream — 3LOD](https://www.metricstream.com/learn/three-lines-defense-model.html)
- **Schuett (2022): Three Lines of Defense adapted specifically for AI companies.** *Applicable, and more targeted than the generic 3LoD explainer above — a citation gap in the prior draft, now filled.* Proposes 3LoD explicitly to "assign and coordinate risk management roles and responsibilities" inside an AI organization, aimed at "decision-makers at leading AI companies, regulators, and standard-setting bodies," with three stated benefits — identifying coverage gaps, strengthening effectiveness, improving board-level oversight — that map directly onto this repo's own gap (a 2nd-line-shaped panel with no 3rd line auditing it). This is the citation that should anchor the "missing 3rd line" claim above; the MetricStream page was written for financial-services audiences generically and carries no AI framing. [Schuett — Three Lines of Defense Against Risks from AI, arXiv:2212.08364](https://arxiv.org/abs/2212.08364)
- **Kerviel / Adoboli / Leeson: the canonical rogue-trading failures the repo's ADR explicitly names.** *Applicable* — confirms the threat-model framing is grounded in real cases where the same actor controlled both the action and the record used to check it; generalizes to "same weights/context/incentive gradient" for an LLM-based system, which is exactly constraint #3's concern — and, per the solo-operator discussion below, generalizes further still to "same human principal" in this repo's specific case. [HSTalks — rogue trading](https://hstalks.com/article/4254/behavioural-patterns-in-rogue-trading-analysing-th/)
- **Man Group AlphaGPT: Idea/Implementer/Evaluator AI roles, with a *separate* human Investment Committee and Technology review layer.** *Most directly transferable real-world example* — an AI-role-differentiated generation team sitting entirely inside normal research process, architecturally distinct from a separate independent-review layer; confirms the two-layer shape First Passage is contemplating is not novel. **Caveat surfaced on closer read of the source:** Man Group's own description of the Evaluator — "built-in consistency checks between idea generation, implementation and evaluation" — reads as plausibly iterative, and the piece never states whether a failed evaluation triggers a refinement loop back to the Idea/Implementer roles or a terminal rejection. This matters directly for Candidate C below: uncritically copying this shape risks reintroducing the evaluator-optimizer pattern Angle 1 already flagged as the pattern to avoid, just relocated inside the generation team. [Man Group — AlphaGPT](https://www.man.com/insights/what-ai-can-do-for-alpha)
- **QuantConnect's Research Validation Agent: a discrete checkpoint, not an iterative partner, in a linear `Ideas → Research → Research Validation → Backtesting → Paper Trading → Live Monitoring` pipeline.** *Applicable and directly load-bearing for Candidate C — a finding present in the prior draft's bibliography and synthesis but never actually scored, now fixed.* The role "acts as a critical opinion, testing whether the statistical foundation is strong enough to continue" against "standards a professional quant team would expect: documented assumptions, explicit diagnostics, and clear pass/fail reasoning," and is offered as a separate, assignable agent distinct from the Research Assistant that does the generating — structurally a gate, not a feedback loop. Given the Man Group ambiguity immediately above, this is the safer real-world template to copy for a one-shot first-line validation role. [QuantConnect — Assistants: Agent Teams for Systematic Research](https://www.quantconnect.com/announcements/20802/assistants-agent-teams-for-systematic-research/)
- **Microsoft RD-Agent(Q): Synthesis/Implementation/Validation separation with a numeric de-dup threshold (IC ≥ 0.99 discards a factor).** *Applicable* — a peer-reviewed (NeurIPS 2025), quantified generation/validation separation directly comparable to the existing K-budget discipline; the transferable lesson is that the *deterministic numeric check* is doing more real independence-work than the "separate LLM role" framing — worth borrowing more than the multi-agent shape itself. [microsoft/rd-agent](https://github.com/microsoft/rd-agent)
- **CAPA: LLM-judges favor similar models; mistakes correlate MORE, not less, as capability rises.** *Most load-bearing finding for constraint #3* — a direct, empirical warning against assuming context-isolation alone is sufficient independence; it blocks literal collusion but not correlated blind spots baked into shared weights. This is now the primary citation (together with the Apple study, Angle 5) for the "differentiate panel/generator persona lineage" recommendation — see the Angle 2 self-attribution-bias correction above for why that paper is no longer used to support this claim. [arXiv:2502.04313](https://arxiv.org/abs/2502.04313)

### Angle 4 — Academic multi-agent debate / LLM-as-judge literature

- **Du et al. (2023): the founding multi-agent-debate result — peer critique/revision improves accuracy on single-question tasks.** *Weakly applicable* — this is debate *among generators* on fast-ground-truth tasks, a different shape from a multi-week research campaign; not evidence for interactive generator↔panel dialogue. [arXiv:2305.14325](https://arxiv.org/abs/2305.14325)
- **2025–2026 re-evaluations: MAD frequently fails to beat single-agent CoT, especially with homogeneous (same-model) debaters.** *Applicable* — warns against assuming "more personas" automatically buys more coverage for any internal a3/a4 role split, since the personas will near-certainly share the same base model. [arXiv:2502.08788](https://arxiv.org/abs/2502.08788)
- **"Debate hacking": competitive debate optimizes for winning the argument (CopMAD); consensus-seeking suppresses genuine disagreement (CosMAD).** *Directly applicable* — names a mechanism for the exact "Kerviel/Adoboli-shaped" threat the ADR cites: interactive back-and-forth between generator and reviewer is the *default* failure mode, not a rare exploit, strongly supporting the panel's existing one-shot, non-interactive design. [arXiv:2510.20963](https://arxiv.org/html/2510.20963v2)
- **Sycophancy/conformity: group accuracy can fall even when correct agents are the numerical majority.** *Applicable* — reinforces no live channel where panel critique and generator rebuttal go back and forth before a verdict is recorded. [arXiv:2509.05396](https://arxiv.org/abs/2509.05396)
- **AI Safety via Debate: the theoretical ancestor of adversarial oversight — requires a symmetric two-sided argument before a judge.** *Applicable, clarifying* — the existing panel is *not* debate in this technical sense; it's a one-sided asymmetric verifier reading a frozen artifact, closer to "safety via consultancy/verification" — worth citing accurately rather than conflating with this paper's mechanism. [arXiv:1805.00899](https://arxiv.org/abs/1805.00899)
- **Judges are internally consistent without being valid ("reliability without validity"); self-preference bias favors own-model outputs; self-correction fails in-context but succeeds when re-presented as externally-authored.** *Applicable, converging evidence* — three findings that (a) a self-consistent panel verdict is not the same claim as a correct one, supporting strictly-advisory framing; (b) same-model favoritism is a real risk requiring differentiated panel/generator prompt style — grounded in CAPA and the Apple panel-correlation result (Angle 3, Angle 5), *not* in the self-attribution-bias paper, see the Angle 2 correction; (c) the panel's fresh-spawn/external-artifact design is doing genuinely different, real work versus same-session self-review, not just ceremony. **The self-correction claim in (c) has a documented lineage worth tracing explicitly, filling a gap in the prior draft that cited only the later paper**: Huang et al. (2023) first established the baseline result that LLMs "struggle to self-correct their responses without external feedback, and at times, their performance even degrades after self-correction" when correcting their own live reasoning in-context; the 2026 Self-Correction Illusion finding builds directly on that baseline by showing the same self-correction capability the model lacks in-context reappears when the identical claim is re-presented as if authored externally — re-presentation, not fresh capability, unlocks it. That two-paper lineage is the specific mechanism validating the panel's frozen-artifact handoff: routing generator output through an external artifact before a second pass reads it is doing exactly the re-presentation the Self-Correction Illusion paper shows matters, on top of Huang et al.'s baseline showing why the same-session equivalent would not work. [Judge reliability](https://arxiv.org/abs/2606.19544) · [Self-preference bias](https://arxiv.org/abs/2410.21819) · [Huang et al. — LLMs Cannot Self-Correct Reasoning Yet, arXiv:2310.01798](https://arxiv.org/abs/2310.01798) · [Self-correction illusion](https://arxiv.org/abs/2606.05976)

### Angle 5 — Agentic-team failure modes and anti-patterns

- **MAST taxonomy: 79% of multi-agent failures trace to specification/coordination problems, not capability; a dedicated verifier stage is "not a silver bullet" (ChatDev still failed 67% of tasks with one).** *Directly applicable* — a base-rate map of where an a3/a4 pipeline breaks (step repetition, reasoning-action mismatch), none of which the panel touches since it only fires post-hoc on frozen artifacts. [arXiv:2503.13657](https://arxiv.org/html/2503.13657v2)
- **Apple: nine frontier LLM judges drawn from *seven distinct model families* still collapse to only ~2 independent votes' worth of information (Kish effective sample size); the best single judge often matches the full panel, and standard aggregation methods close "at most 11% of this gap, even with access to the correct answers."** *Most damaging finding against an implicit assumption — corrected here from the prior draft, which mischaracterized the tested panel as same-family.* The panel was already **cross-vendor heterogeneous**, not same-family, and it still collapsed — which makes this a *stronger* result than the prior draft credited, not a weaker one: real cross-vendor diversity did not fix correlated judge error, and the 11%-recovery ceiling held even with ground truth available for the aggregator to use. This directly bears on, and reshapes, this note's own "Open questions" discussion of a second model family — see the reconciliation there. [Apple ML Research](https://machinelearning.apple.com/research/correlated-llm-evaluation-panels)
- **Secret Collusion Among AI Agents: Multi-Agent Deception via Steganography — communicating AI agents may develop steganographic (hidden-channel) coordination; GPT-4-class models already show "a capability jump suggesting the need for continuous monitoring of steganographic frontier model capabilities."** *Applicable to constraint #3, but scoped narrowly — a citation present in the prior draft's bibliography but never discussed, now fixed.* This is the sharpest available warning that "the generator and reviewer never talk" is not automatically true just because no chat channel is wired between them: any surface both sides can write to and later read (a commit message, a file-naming convention, a shared manifest field) is technically a channel a sufficiently capable model could use covertly. The panel's actual design already closes the specific channel this paper worries about — per the repo's own ADR, the frozen artifact is read-only from the panel's side and the panel's append-only log is write-only from the generator's side — so today's practical exposure is low. The paper's real value here is as the citation for *why* those two one-way constraints are load-bearing rather than incidental, and as an argument against ever adding a shared read-write surface between generation and panel personas (a shared scratch file, a shared TODO list) even for convenience as a3/a4 formalizes. [Secret Collusion among AI Agents, arXiv:2402.07510](https://arxiv.org/abs/2402.07510)
- **Algorithmic monoculture: shared foundation models correlate failures even under normal operation; full convergence on the "best" model can lower collective accuracy versus a heterogeneous mix.** *Applicable, theoretical grounding* — a fleet of personas on one base model is a monoculture no matter how cleanly session state is separated; the human operator, not additional same-family personas, is the actual diversity-injecting component. [PNAS 2021](https://www.pnas.org/doi/10.1073/pnas.2018340118)
- **Trust but Verify! A Survey on Verification Design for Test-Time Scaling — surveys verifier design (prompt-based; fine-tuned discriminative/generative) for judging candidate outputs across process- and outcome-level checks.** *Applicable — grounds a claim used elsewhere in this note that was previously uncited.* This is the direct source for the generator/verifier-asymmetry argument the Cross-cutting synthesis below relies on (verification treated as a structurally distinct, often cheaper sub-problem than generation in the test-time-scaling literature). It does not itself resolve whether that asymmetry holds for statistical/backtest-style claims specifically — its focus is reasoning, math, and code test-time scaling — so the extension to this repo's use case is an explicit analogy, not direct evidence, and is named as such where it is used. [Trust but Verify! Verification Design for Test-Time Scaling, arXiv:2508.16665](https://arxiv.org/abs/2508.16665)
- **"Verification Theatre": real verification requires injecting information the closed chain doesn't already contain.** *Applicable, adversarial to the panel's own self-conception* — the closed-chain argument operates at the base-model substrate level, not the session level; the panel's real, unstated safety property is the human GO/NO-GO requirement, not model independence — argues against ever treating panel sign-off as a substitute for that human check. **This framing is extended in Cross-cutting synthesis below to a second, previously unexamined risk: operator attention economics under higher review throughput.** [Verification Theatre](https://hip1.github.io/The-Verification-Theatre/the-verification-theatre.html)
- **Evaluator/reward-hacking: generators can learn to satisfy an evaluator's surface heuristics rather than its actual intent; isolation failures worsen this when generator and evaluator share tooling/process.** *Directly applicable to constraint #2* — this generic failure mode has already manifested non-adversarially in this repo (a checker-green brief with 6 real BLOCKERs, per MEMORY.md); keep panel acceptance criteria and any generation-team self-checks structurally distinct, not merely differently-prompted. [arXiv:2604.13602](https://arxiv.org/html/2604.13602v1)
- **General anti-over-engineering guidance: minimal agent count, add an agent only when a specific bottleneck justifies added coordination cost.** *Applicable* — combined with MAST, argues for a small number of well-specified roles over an elaborate fleet if a3/a4 are formalized at all. [LangChain — how and when to build multi-agent systems](https://www.langchain.com/blog/how-and-when-to-build-multi-agent-systems)

## Cross-cutting synthesis: the generation/audit seam

**The sweep supports structuring a3/a4 on the generation side, but structuring the seam is a separate design problem, and evidence for one does not validate the other.** Real precedent exists for role-differentiated AI generation teams sitting inside a normal research process — Anthropic's own orchestrator/subagent Research system, Man Group's Idea/Implementer/Evaluator split, Microsoft's RD-Agent(Q) Synthesis/Validation separation, QuantConnect's pipeline-staged Research Validation Agent, hedge-fund pod structures. Only one of these — Man Group — is actually documented as sitting alongside a *separate, external* higher-independence review layer (a distinct human Investment Committee and Technology review); it is the one clean, real-world confirmation that this two-layer shape is not novel. The other four demonstrate generation-side role differentiation on its own terms, without evidence one way or the other about a further external layer, and one of them points the other way outright: Anthropic's own orchestrator/subagent system is cited in this sweep purely for its internal delegation and context-isolation mechanics, with no documented external review stage attached to it; RD-Agent(Q)'s and QuantConnect's validation stages are, per Candidate C below, explicitly first-line/pod-risk-desk-shaped and are never described as second-line independent review; and hedge-fund pods are the one example that actively illustrates the *opposite* point — Angle 3 is explicit that a pod's always-on risk desk is a *constraint* analogue, not the panel's *periodic-independent-review* analogue. So the sweep does not converge on "every generation team needs and gets a separate review layer" as a general empirical pattern across all five examples; it converges on something narrower, and still load-bearing: no source recommends collapsing generation and review into one layer, and Man Group is a live, real-world case where the two coexist as architecturally distinct functions. That narrower claim, not a five-for-five confirmatory pattern, is what the rest of this section rests on. That two-layer shape is exactly what First Passage already has (ad hoc generation below, the persona panel above), and nothing in the sweep argues for collapsing it into one layer.

**The panel's existing design is validated by convergent evidence from multiple, otherwise-unrelated literatures**, and should be left alone rather than "upgraded." Anthropic's context-engineering "isolate" primitive, the mechanistic finding that externally-re-presented claims unlock self-correction ability a model cannot apply to its own live reasoning (Huang et al. 2023 → Self-Correction Illusion 2026, traced explicitly in Angle 4), generator-verifier asymmetry theory — verification treated as a structurally distinct, often cheaper sub-problem than generation in the test-time-scaling literature (Trust but Verify!, arXiv:2508.16665; extended here from reasoning/code tasks to this repo's backtest-artifact case by analogy, not by direct evidence) — and finance's SR-11-7/18f-4 independence framing all point the same direction: fresh-spawn, frozen-artifact-only, one-shot, no-rebuttal review is the *correct* shape, not a compromise. The academic debate literature adds a sharp reason **not** to improve it toward anything more interactive — debate-hacking and sycophancy findings show that letting a generator and reviewer talk back and forth is the default route to exactly the consensus-collapse the ADR's threat model names, not a hypothetical edge case.

**But the panel's independence guarantee has a documented blind spot that predates and is untouched by any a3/a4 reorganization: correlated error from a shared base model.** CAPA, the Apple "two effective votes" result, self-preference bias, and algorithmic-monoculture theory all say the same thing from different angles — context-isolation blocks literal collusion and prompt-sharing, but it does **not** block the reviewer and generator making the same category of mistake because they run on the same weights. This means the panel was already doing less independence-work than its SR-11-7 framing implies, and formalizing a3/a4 doesn't make that worse, but it also means a structured generation team should not be sold internally as "now the panel's independence is fully robust" — it wasn't fully robust before, and nothing about adding roles to the generation side changes that fact. The corrective is procedural, not organizational, and modest rather than curative: differentiate panel-persona prompts/lineage from generator-persona prompts/lineage even though both are Claude — grounded in CAPA's same-family-favoritism finding. The Apple result belongs here mainly as a caution against overstating what that differentiation buys, not as evidence that it works: Apple's panel had genuine cross-vendor heterogeneity — nine judges, seven distinct model families, real weight-level diversity, a materially *stronger* manipulation than same-weights prompt/lineage differentiation — and it still collapsed to ~2 effective independent votes, with standard aggregation closing "at most 11%" of the gap even given the correct answers. If that much diversity barely moved the needle, a same-weights, prompt-only difference should be expected to help only at the margin, consistent with how Open Questions treats the analogous but strictly stronger case below (a genuine second model family). The move that actually escapes the correlated-mistake liability, per this same body of evidence, is leaning on deterministic/numeric checks (K-ledger arithmetic, RD-Agent-style dedup thresholds, cost-law pre-screens — see also Option E below) wherever possible instead of a second LLM judgment; persona/lineage differentiation is worth doing because it is close to free, not because either citation shown here demonstrates it closes the gap.

**A second blind spot, specific to this repo, is not raised by any of the five literatures on their own terms and needs to be named directly: every organizational-independence analogy used above — SR 11-7, 18f-4, Three Lines of Defense, the hedge-fund pod's always-on risk desk — assumes plural human staff with genuinely separate reporting lines, compensation structures, and career incentives.** First Passage has none of that. It is a solo-operator pipeline: the same human configures every persona's prompt, launches every session, and reads every output at every layer, whether that layer calls itself "generation," "first-line validation," or "second-line review." SR 11-7's independence is explicitly anchored in organizational facts a persona spawn cannot literally have (a distinct reporting line, compensation not tied to the model's outcome) — Angle 3 flags this once in passing, but the sharper question the sweep's own material raises and never asks is this: does adding more formal-looking roles — a first-line Research Validation agent, plus the existing second-line panel, plus, under Candidate D, a fully mirrored front-office org chart — make the solo operator *more* likely to defer to the appearance of process independence, precisely because it now looks like a real organization, even though the underlying single-human-accountability structure has not changed at all? This is arguably the most repo-specific instance of the Kerviel/Adoboli threat model the ADR names: in the classical cases, the failure was one actor controlling both the action and the record used to check it. Here, no matter how many Claude personas sit between generation and ratification, the operator is that one actor at every layer — the personas change what gets *shown* to the operator, not who is ultimately checking whom. No source reviewed in this sweep tests or even discusses this configuration (a single human principal instantiating both sides of an "independence" structure), so this is named as an open, unresolved risk — see Open Questions — rather than presented as a sourced finding.

**A related, also repo-specific gap: none of Options B, C, or D below were evaluated for their effect on operator attention.** "Verification Theatre" is already cited above for the claim that the panel's real, unstated safety property is the human GO/NO-GO requirement, not model independence — and every option except A raises raw candidate-generation throughput via parallel fan-out. For B and D that raw increase and the panel-facing increase are the same number: output moves toward the panel effectively unfiltered, so a plausibly higher rate of GRAND-tier ratifications and strict-D2 STRATEGIC-tier Deletes reaches the human operator for that GO/NO-GO. Candidate C complicates this rather than escaping it: its first-line validation gate is explicitly built to filter that same fan-out-driven output before it reaches the panel (see Candidate C's own "reduces noise reaching the independent panel" tradeoff below), so C's *net* effect on panel-facing volume relative to today's baseline is a different, unmeasured claim from B's or D's — it depends on the gate's catch rate, which no source in this sweep measures, and net volume could still land above A's baseline even after filtering. A higher volume of review requests hitting the same one human is a fatigue-driven rubber-stamping risk that is completely independent of any model-level convergence risk discussed above — it would exist even with a perfectly heterogeneous, perfectly independent review panel. No source in the sweep addresses this; it is named here as a design constraint any of Options B–D should carry explicitly (for example, a hard cap on ratifications-per-week the fan-out is allowed to generate, set independently of how many subagents are technically available to run, and — for C specifically — not assumed satisfied by the validation gate's mere existence until its catch rate is actually measured) rather than left as an implicit assumption that more throughput is free.

**Concretely, what transfers to the seam design:**
- **Never let a3/a4 subagents and panel-reviewer subagents be siblings in one parent session or Workflow run.** The sibling-roster mechanic in Claude Code subagents is a real leak path; the panel must be invoked as its own top-level run against the frozen artifact only.
- **Keep the interface a structured artifact, never a conversational trace.** This matches MetaGPT's document-handoff pattern and is already how this repo's frozen decision docs work; AutoGen's full-shared-history default is the negative example to avoid, and LangGraph's explicit `full_history`/`last_message` handoff-scope lever is the right mental model — the panel side should always use the equivalent of zero shared history.
- **No interactive rebuttal loop, ever**, between generation-team output and the panel's verdict — evaluator-optimizer, debate-hacking, and sycophancy findings all point the same direction, and any first-line "Research Validation" role added on the generation side (Candidate C) must be built the same way for the same reason — see the QuantConnect-vs-Man-Group contrast there.
- **Keep the panel's acceptance criteria and past-findings log unreadable to the generation team's prompts, skills, or shared tooling.** This is both the reward-hacking/evaluator-gaming literature's generic warning and a concrete instance already observed in this repo (a checker-green brief that still had 6 real BLOCKERs) — the panel's append-only log stays write-only from the generator's side, exactly as the ADR already specifies, and this must not erode as more generation output starts flowing toward it. It is also the specific channel Secret Collusion (Angle 5) warns against ever turning into a shared read-write surface.
- **An internal generation-team validation role (RD-Agent's Validation stage, QuantConnect's Research Validation Agent, Man Group's Evaluator) is a legitimate and useful first-line/pod-risk-desk-shaped addition — but it is not, and must not be presented as, second-line independent review.** The panel remains the only second-line function; there is currently no third line auditing the panel itself, which the Three-Lines framing (Schuett, AI-specific) surfaces as a real, separate gap.
- **K-budget discipline has to be owned centrally by whatever orchestrates a3/a4 fan-out, and this repo already has the concrete mechanism that requirement maps onto — though not yet the enforcement to back it.** `lab/discovery/register_search.py`'s `open_run`/`close_run` CLI is the actual K-ledger write path: `open_run` declares `K` (`search_space_size`) into a `discovery_manifests/*.json` entry before any scoring happens, and `close_run` may only *lower* it to `executed_k`, never raise it (per the `2026-07-26-mechanism-counterparty-constraint-boundaries.md` ADR §2-C). `lab/research_utils/axis_screen.py`'s Clause-K gate then reads `K_intrinsic` from that frozen manifest — per the `2026-08-04-family-k-bank-disclosure-not-gate.md` ADR, family-level `K_banked` is disclosure-only, and `K_eff = K_intrinsic` is what actually gates. Concretely, "the orchestrator owns ledger updates centrally" means: only the orchestrating process calls `register_search.py open`/`close`, never a miner or harvest subagent directly. Today that rule has no technical teeth: the CLI itself performs no caller-identity check of any kind — it only refuses to reopen an already-used `run_id` — so anything with Bash access, including a spawned subagent, can invoke `open`/`close` exactly as the orchestrator would. Making the rule real requires a specific, named step this option must build in, not assume: scope each miner/harvest subagent's tool allowlist at spawn time to exclude Bash/CLI access to `register_search.py` and any write path into `discovery_manifests/`, so a subagent can only return findings for the orchestrator's own process to register. That is a real, application-level control — a documented Claude Code primitive (subagents can be spawned with a restricted toolset) — but it lives entirely in how each subagent is configured at dispatch, not in the ledger itself, so a misconfigured spawn silently reopens the exact risk this rule exists to close: if N parallel a3 miner subagents can each open their own run, the ledger either double-opens (over-counting, unfairly killing an instrument's headroom) or under-counts (each subagent declaring a small `K_intrinsic` for what is jointly a much larger search — exactly the ADR's own named forbidden move, "quietly declaring `K_intrinsic = 1` for a design that actually searched"). Anthropic's own duplicated-subagent failure is a direct structural analogy to this exact risk, just relocated from "wasted work" to "wasted work that also corrupts a frozen multiplicity ledger." a3's fixed TNEC-1 search space (`docs/spec/2026-08-08-tnec-1-tradeify-necessary-conditions.md`) favors pre-partitioning the space into non-overlapping mechanism/instrument cells *before* declaring `K` — each cell's size folding into one combined `search_space_size` at a single `open_run` call, made once, by the orchestrator, before any cell's subagent starts work. a4's adaptive harvest is harder: its "explicit, pre-registered rule for when a new sub-task may spawn mid-campaign" must concretely mean any new axis a harvest subagent wants to pursue gets added to the declared `search_space_size` *before* that axis is scored, never after seeing its result — the same constraint the ADR's forbidden-moves list already states for the single-agent case; formalizing a4 as a team does not relax it, it only moves the discipline from "the operator remembers to declare it" to "the orchestrator's spawn-time tool-scoping enforces it before dispatching that sub-task" — reliable only to the extent that scoping is actually configured correctly, not a guarantee the ledger itself provides.

**What does not transfer:** production-service engineering (checkpoints, rainbow deployments) is irrelevant to session-bounded campaigns; AutoGen/CrewAI's shared-context group-chat pattern is acceptable *only* for generation-internal *coordination* — dividing and tracking work among miner or harvest subagents so they don't silently diverge — and must never be reused at the generator→panel boundary; CrewAI's "manager validates its own workers" pattern is a narrower case and does not get the same internal-only pass: any role that *grades or gates* a3/a4's own output, not merely coordinates it, inherits the seam's no-iteration rule regardless of which side of the seam it sits on, for the same evaluator-optimizer reason (Angle 1) — Candidate C's first-line validation role below is specified as strictly one-shot for exactly this reason, applying this same rule to the one generation-internal role that actually does grading rather than coordination, not carving out an exception to it. Cognition's "give agents more shared context" prescription is correctly aimed at within-team coordination problems (don't fragment one hypothesis across subagents blind to each other's assumptions) and would be actively wrong advice if extended to the seam.

## Candidate structural implications

*(Framed as options for discussion, not a proposal ready for ratification.)*

**These lettered options are not a single global choice for "the generation layer" — they can, and per Angle 1's own findings probably should, be applied asymmetrically across a3 and a4.** Angle 1 already establishes the two workstreams have different shapes: a3's fixed TNEC-1 search space is a clean, pre-registerable fit for parallel fan-out, while a4's adaptive harvest is structurally harder to pre-register and carries the sharper version of the K-ledger risk discussed under Option B, since — per Open Questions — no source has actually run an a4-shaped mid-campaign spawn declaration against a K-ledger gate and reported what broke. A defensible staged rollout moves a3 to B (or further) sooner, capturing its cleaner throughput benefit, while holding a4 at A or at Option E's deterministic-gate-only tier until its mid-campaign K-declaration rule has actually been exercised and shown safe in practice. This is a separate axis from whether a3 and a4 are eventually organized as one team or two, which is a naming/organizational-identity question the sweep does not address (see Open Questions) — a3 and a4 can sit at different letters on this list while still being called one team, or the same letter while being called two.

**A — Keep a3/a4 ad hoc; formalize only a spawn-prompt task-boundary template.** No new personas, no fan-out — where "fan-out" means parallel, multi-subagent coordination specifically; A's boundary does not exclude delegating to a single subagent per campaign in sequence (using Claude Code's own context-isolation primitive to keep the operator's main session clean of mechanical mining/harvest work), since a lone caller has no one to double-open the K-ledger against and none of Option B's coordination-surface cost applies — just apply Anthropic's own delegation-contract checklist (explicit objective, output format, pre-registered scope, K-ledger touchpoint) to today's single-session (or single-subagent) a3/a4 work, directly targeting MAST's finding that 79% of multi-agent failures are specification problems and Anthropic's own duplicated-subagent failure. Cheapest option and adds zero new coordination surface, and carries neither of the two repo-specific risks named above (appearance-of-independence deference, operator-review-volume fatigue), since it changes nothing about how much reaches the operator or how many roles exist. Tradeoff: gets none of the throughput benefit real parallel fan-out could offer, and its quality depends entirely on the human operator writing a good task boundary every single session — it doesn't structurally prevent anything, it just makes good practice easier to repeat.

**B — Bounded, per-campaign fan-out (not standing personas).** An a3 orchestrator pre-partitions the TNEC-1 search space into mechanism/instrument cells (declaring the combined `search_space_size` once, centrally, via `register_search.py open_run`, per the K-ledger grounding in Cross-cutting synthesis above) and spawns N miner subagents against non-overlapping cells, synthesizing to one frozen candidate manifest; a4 spawns a bounded set of harvest subagents with an explicit, pre-registered rule for when a new sub-task may be spawned mid-campaign (any new axis is declared into `search_space_size` before it is scored, never after). Mirrors Anthropic's Research-system shape and RD-Agent(Q)'s Synthesis/Validation split, buildable today purely with Agent + Workflow. Tradeoff: real complexity increase (more MAST-taxonomy coordination surface); a real, though not campaign-specific, token-cost premium — Anthropic's own published figures for its production research system are that single agents run **~4× the tokens of a chat interaction** and its multi-agent system runs **~15× the tokens of a chat interaction** (two distinct comparisons, both against chat, not against each other, and not measured for a3/a4's specific shape — treat "meaningfully more expensive per campaign" as the honest claim here, not a specific multiplier). K-budget safety is not a property this design gets for free: `register_search.py` has no caller-identity check, so "only the orchestrator calls it" is a convention today, not a control — this option only becomes K-budget-safe once each miner/harvest subagent's tool allowlist is explicitly scoped at spawn time to exclude `register_search.py`/`discovery_manifests/` write access (the concrete mechanism specified in Cross-cutting synthesis above), and even then that safety holds only as reliably as that scoping is actually configured at every spawn, not as a guarantee the ledger itself provides. Two further costs cell-partitioning does not by itself solve: it stops subagents from re-searching the same ground, but not from silently diverging on shared implicit assumptions (cost-model conventions, contract-value defaults, session/TZ handling) the cells still hold in common — exactly the fragmentation risk Cognition's critique (Angle 2) names, and one this repo has already produced non-adversarially with a single human operator working alone, not even a fan-out (the Guardian/Aegis chart-TZ defect; the static-equity recompute miss) — closing it needs the same explicit, shared assumptions spec Option A proposes, written once and handed identically to every miner cell before fan-out begins, not a byproduct of partitioning the search space; and the same-base-model correlated-error risk named against Candidate D below (algorithmic monoculture, Angle 5) applies here too, in miniature — N parallel same-model miner subagents share blind spots just as a standing mirrored org chart would, so cell-partitioning buys search-space coverage, not independence, and should not be read as diversifying anything but which slice of the space gets searched. Finally, it increases review-request throughput toward the panel, which is the operator-fatigue risk named in Cross-cutting synthesis and not otherwise priced by this option.

**C — Option B plus a standing, first-line "Research Validation" role inside the generation team**, modeled on RD-Agent(Q)/QuantConnect's Research Validation Agent, ideally leaning on numeric/deterministic checks (cost-law pre-screen, dedup threshold, K arithmetic) rather than a second LLM judgment call, per CAPA's warning that same-family LLM judges share blind spots — see Option E below for a way to get much of this same deterministic-check benefit without requiring B's fan-out to exist first; the two are not mutually exclusive, but this option assumes B is already built. **This role must be specified as strictly one-shot — a single pass/fail gate reading a frozen intermediate artifact, never an iterating partner to the generator/implementer** (per the coordination-vs-validation distinction in Cross-cutting synthesis's "What does not transfer": generation-internal *coordination* may share context, but any role that *grades or gates* a3/a4's own output — including this one — carries the same no-iteration rule as the generator↔panel seam itself, for the same evaluator-optimizer reason, Angle 1). That constraint has to be explicit because the two nearest real-world models diverge on exactly this point: QuantConnect's Research Validation Agent is a confirmed discrete checkpoint in a linear pipeline (`Ideas → Research → Research Validation → Backtesting`), the safe template to copy; Man Group's AlphaGPT Evaluator is described only as having "built-in consistency checks between idea generation, implementation and evaluation," which reads as plausibly iterative and is never confirmed either way in the source. Copying the Man Group shape uncritically would quietly reintroduce the evaluator-optimizer feedback loop Angle 1 already named as the pattern to avoid — just relocated inside the generation team instead of at the generator↔panel seam, which does not make it safe, only differently placed. The role should also receive the frozen intermediate artifact via a fresh, isolated subagent context — Anthropic's "isolate" context-engineering primitive — rather than as a continuation of the generator/implementer's own assistant turn; this is a narrower requirement than the panel's own top-level-run isolation (the sibling-roster leak Angle 1 warns about is a different mechanism, and doesn't obviously apply to a role that never claims independence in the first place), but it is what actually preserves the self-attribution-bias-avoidance property Angle 2's corrected reading identifies, and it costs nothing extra to build in from the start. Tradeoff: intended to reduce noise reaching the independent panel and matches a clean pod-risk-desk / Three-Lines shape — but that is a filtering *intent*, not a measured effect: the underlying fan-out (via Option B) still raises raw generation volume, no source in this sweep measures this gate's actual catch rate, and until it is measured, C should not be assumed exempt from the operator-fatigue throughput safeguard named in Cross-cutting synthesis — size that safeguard against C the same as B and D until real numbers say otherwise. It must be built with the same kind of technical access boundary specified for the K-ledger above, not a softer version of it: the validation subagent's tool/file scope excludes read access to the panel's acceptance-criteria artifact and past-findings log (to avoid the evaluator-gaming pattern already observed once in this repo), and must never be described to the operator as equivalent to independent review — it's first-line only, and adding it does nothing to close the still-open gap of nothing auditing the panel itself. It also adds one more formally-named role for the solo operator to hold in mind as "another check happened," which is precisely the appearance-of-independence risk named in Cross-cutting synthesis — worth building, but worth naming to the operator explicitly as first-line-only, every time it fires, not just at design time.

**D — A fully mirrored front-office-shaped generation team** — standing personas ("Head of Discovery," "Mining Analyst," "Harvest Analyst") paralleling the CIO/Head-of-Research/Staff structure, with its own versioned charter like the panel already has. Tradeoff: highest ceremony and cost, and the strongest sweep evidence here (algorithmic monoculture, correlated-errors-rise-with-capability, LangChain's minimal-agent-count guidance, Cognition's coupling critique) argues that role/headcount is not itself protective — a fleet of same-base-model personas can even reduce collective accuracy versus a smaller, more heterogeneous setup. Its actual benefit is organizational legibility (a future reader can audit "who did what" cleanly) rather than robustness, and that narrower benefit is what it should be weighed against, not against safety per se. Of all five options this one carries the appearance-of-independence risk named in Cross-cutting synthesis most acutely — a full mirrored org chart run by one human is the closest this repo could come to the literal Kerviel/Adoboli shape (one actor, dressed as many desks) — and it maximizes review-request throughput, so it inherits the operator-fatigue risk at its largest scale too. Both risks are currently unpriced by any source in the sweep; see Open Questions.

**E — Option A plus a deterministic, non-agentic validation gate (no fan-out, no new persona).** Keep a3/a4 exactly as ad hoc as Option A, but add a small, non-LLM script that runs on every candidate before it is scored or registered: a K-arithmetic cross-check against `register_search.py`'s own `open_run`/`close_run` values, an RD-Agent-style dedup/IC threshold, and/or a cost-law pre-screen. This is the shape Cross-cutting synthesis's own most-trusted corrective actually is — deterministic/numeric checks are the one thing that body of evidence shows escaping the correlated-mistake liability that persona/lineage differentiation only partially addresses — decoupled here from any fan-out or persona at all, since a numeric threshold does not require N parallel subagents to exist first. Zero new coordination surface (none of MAST's 79%-specification-problem failure mode applies, since there is nothing to coordinate), zero new persona for the solo operator to over-trust (sidesteps the appearance-of-independence risk named in Cross-cutting synthesis), and no increase in candidate throughput toward the panel (sidesteps the operator-fatigue risk named above) — if anything it reduces panel-facing noise by catching bad candidates before they are ever registered. Tradeoff: captures none of B's/C's/D's throughput or search-coverage benefit — it is a quality gate on today's single-session output, not a way to search more of the space faster — and a numeric threshold is only as good as what it is set to catch; K-arithmetic and RD-Agent-style dedup thresholds are well-specified today against this repo's own ADRs, but a cost-law pre-screen or any other new deterministic check would need its own pre-registration before being trusted as a gate, the same discipline this repo already applies to everything else. E and C are not mutually exclusive — C's first-line role could be built as a thin wrapper around exactly this gate — but E gets much of the same deterministic-check benefit without requiring B's fan-out to exist first, which, per the asymmetric-adoption note above, makes it the natural place to hold a4 (the harder-to-pre-register workstream) while a3 moves to B.

## What the sweep did NOT settle / open questions

- **Whether the panel's independence is doing more procedural-firewall work than actual model-diversity work is not measured for this repo specifically.** Apple's "two effective votes" figure comes from a different panel/task setup; the ADR already gestures at a cheap, repo-native falsifier (rescue rate / disagreement rate on real panel firings) that could measure this directly, but it has not been run.
- **Whether a genuinely different model family for at least one review lens is worth the deviation from "no new infrastructure" was not resolved — and the note's own strongest cited source already leans toward "not by itself."** A second-vendor API call is a small integration rather than a platform, so whether that crosses the spirit of constraint #1 is a judgment call the sweep surfaces but does not decide. But this framing needs to be read against the Apple panel-correlation study directly, not treated as a fully independent open question (a tension left implicit in the prior draft): that panel was *already* nine judges across seven distinct model families — real cross-vendor heterogeneity, not the same-family setup this note originally, and incorrectly, attributed to it (see the Angle 5 correction) — and it still collapsed to ~2 effective independent votes, with standard aggregation closing "at most 11%" of the gap even given the correct answers. If cross-vendor diversity at that scale barely moved the needle in a directly analogous setting, one added model family for one review lens here should be expected to help only marginally, not to solve the correlated-failure problem this note otherwise treats as open. The honest resolution: a second model family is very likely still worth doing (cheap, right direction), but should not be sold, even provisionally, as closing the correlated-error gap — per Apple's own numbers, that gap looks structural, not a vendor-count problem.
- **No source directly tested K-budget/multiplicity accounting under a multi-subagent generation team inside a pre-registration-gated research pipeline of this exact shape.** The finance staged-gate sources are structurally similar but not identical; the mapping from Anthropic's "duplicated searches" failure to "duplicated trial-count against the K-ledger" is an analogy, now made concrete against this repo's actual `register_search.py`/`axis_screen.py` mechanics in Cross-cutting synthesis, but it remains an analogy, not a verified equivalence — no source has actually run a multi-agent generation team against a K-ledger gate of this kind and reported what broke.
- **The debate-hacking/sycophancy evidence against interactive generator↔panel loops comes entirely from single-question, fast-ground-truth tasks (math, factuality).** None of it was tested on multi-week research-campaign artifacts with delayed, statistical ground truth (backtest results) — the "keep it one-shot" conclusion is well-supported directionally but extrapolated, not directly evidenced, for this task shape.
- **Whether a3 and a4 should be organized under one generation team or stay structurally separate was not addressed by any source.** The parallelization-vs-orchestrator-workers taxonomy suggests they have genuinely different shapes (fixed search space vs. adaptive harvest), but nothing in the sweep speaks to whether unifying or separating their team structure is preferable.
- **Whether formalizing generation-side roles increases the risk that the solo operator defers to the *appearance* of independence rather than any real independence gain was not addressed by any source, because no source in the sweep considers a single-human-principal configuration at all.** See the dedicated discussion in Cross-cutting synthesis above; this is the most repo-specific unresolved risk the sweep surfaces, and this note does not resolve it — a design that wants to guard against it would need a mechanism outside anything reviewed here (e.g., an explicit periodic reminder to the operator of what each layer does and does not check, refreshed independently of the panel/generation-team artifacts themselves).
- **Whether higher-throughput generation (Options B–D) raises the rate of ratifications/Deletes reaching the operator enough to create fatigue-driven rubber-stamping risk was not measured or estimated by any source.** No source addresses reviewer-attention economics at the volume First Passage would actually produce; see Cross-cutting synthesis for the reasoning chain (Verification Theatre's human-GO/NO-GO framing, plus Options B–D's explicit throughput aim) that surfaces this as a real, currently unquantified risk rather than a resolved one.

## Addendum — Head of Engineering owns generation-orchestration tooling (design conversation, 2026-08-19, later)

**Status: a candidate direction from a design conversation, not a ratification.** No ownership-map
edit, ADR, or persona-file change has been made. Recorded here so the reasoning survives past this
session, per this note's own "appearance-of-independence" and "operator attention economics" themes —
the same discipline this note argues for is worth applying to itself.

**The question that came up:** if Option E's B+C-hybrid (bounded per-campaign fan-out plus a
first-line Research Validation role) is ever built, and the orchestrator role is given a name and a
versioned charter (matching the review panel's own convention, for legibility) — does that clash with
the existing persona hierarchy, or mesh with it?

**Considered and rejected: expanding Head of Research's own role to include execution.** Head of
Research already sits in the review chain for a3/a4 — per its own file, it participates in the
strict-D2 STRATEGIC-tier Delete trigger "either as proposing office (1st line) or independent
challenger (2nd line)." Its `Independence rule` is identical boilerplate to every other panel persona:
"Spawned fresh per review, reading only the frozen decision artifact under review... never the
proposing session's live reasoning." Making that same identity also the live executor of a3/a4
generation would be a literal instance of the Kerviel/Adoboli threat model this whole panel is built
against — not an analogy to it, since the actor auditing a decision and the actor who produced it
would share persona identity, log, and lineage. It also structurally doesn't fit: "spawned fresh,
reads one frozen artifact" is the wrong shape for a persistent, multi-session orchestration job.

**Resolution: Head of Engineering already owns exactly this pattern for a6, and the same shape
extends cleanly to a3/a4's orchestration mechanism.** Its own file: *"personally performs the
AI-agent-orchestration function (decompose, freeze specs, own the claim manifest, review, integrate,
adjudicate)... rather than delegating it to a separate staff seat"* for a6 (Cursor-fleet worker
capability) — and the ownership map already records that split: `Head of Engineering primary, Head of
Research secondary`. The same split applied to a3/a4: Head of Engineering would own the orchestration
**mechanism** (the Workflow script, the discipline that only the orchestrator ever calls
`register_search.py open`/`close`, the subagent dispatch pattern) as infrastructure — not the
persona itself executing live, but a domain/ownership assignment, same as a6's ephemeral Cursor
workers are owned without being rostered. a3/a4 **content** ownership stays exactly as it is today,
unchanged: Head of Research remains the first-line reviewer, now reviewing the output of a tool
Engineering owns rather than of a fellow reviewer wearing a second hat. Domains stay cleanly
separable — Engineering never sits in the review chain for a3/a4 content Deletes, Research never
executes — so there is no dual-hat collapse.

**What would NOT mesh:** spawning the persona "Head of Engineering" itself as the live, stateful,
multi-session executor. Its file carries the same spawn-fresh-per-review boilerplate as every other
panel member; treating it as a standing operational role repeats the exact structural mismatch named
above, just relocated to a different seat.

**Net, if this direction is ever acted on:** cheapest of the options discussed for this seam — an
ownership-map extension (or a small new pursuit record sibling to a5's R&D tooling lane) plus a
Primary/Secondary row mirroring a6's exact shape, not a new roster entry requiring its own
independence-rule ratification.
