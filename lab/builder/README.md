Rules the engine enforces:
- **Inputs fail closed.** Every input the engine reads has a stated condition, and a load that breaks one aborts the run before any gate result exists. The invariant table is in the PR that introduced this rebuild, and each row has a test in `tests/lab/test_builder/`. Nothing degrades to a skip, a default or a warning. The one deliberate exception is a day the compiler can't trade, and it is counted in `report.skipped_days`.
- **Ledger first.** A card is appended before any bar is read, and the engine refuses a card that isn't in the ledger.
- **Pinned inputs.** run.yaml pins the sha256 of every data file, the book and the calendar. A supplied book must cover `min_overlap` development sessions.
- **Causal exits.** A position still open on a day with no bar at or after `flat_at` (and not stopped or targeted out) is `unresolved`, with no exit price. One unresolved trade in a card's development sessions, or in a 5d neighbour's, makes the card's verdict `unresolved`, reported with the count and dates; it is never a survivor. In the holdout it spends the look and fails it. Entries read only the bars up to the entry bar.
- **Splits pinned by date.** Each `data` entry carries `split: {dev_end, holdout_end}`, optionally with `dev_start`. Development = dev_start ≤ sessions ≤ dev_end; holdout = dev_end < sessions ≤ holdout_end; other sessions are in no gate and not in the holdout. Every given end must be a session date of the loaded export. Bars before `dev_start` only warm up ATR.
- **Missing bars.** TradingView omits a 15m bar in which nothing traded, so the loader counts gaps (`gap_sessions`, `days_without_open_bar`) instead of refusing them; a day without its open bar is not a session. A missing bar is a no-trade interval. A card's range is fixed clock slots from the session open; a day missing any of them is skipped as `range_gap` for that card (each 5d neighbour applies the rule to its own range). A flat_at on a missing bar exits at the next real bar's open, or the trade is `unresolved` if none comes before 17:00.
- **Frozen calendar.** `calendar: {path, sha256}` names the admitted `ops/calendars/cme_holiday_calendar_2022_2026.json` (sha256 `2698f2688cce582b08df58516fd770fa4a71a18de04870d9c14511731ea181e9` at admission). The engine reads only `schema` (must be `cme_holiday_calendar/v1`), `coverage_start`, `coverage_end` every `entries[].date` and each entry's `*_status` fields. **An entry date is closed only when at least one recorded status is not `NORMAL`** (Joshua 2026-11-03, option B on PR #1045); an all-`NORMAL` row is informational and its session is traded. An entry with no `*_status` field or a status outside `EARLY_CLOSE`/`FULL_CLOSURE`/`NORMAL` aborts the load. A session on a closed date is not traded (skip reason `calendar_exception`) but stays a session for the split and the daily series, at zero P&L. Every development and holdout session must lie in the coverage window. The file keys closures to the CME trade date; for the day session the engine reads (session open to 17:00 ET) the wall-clock date is that trade date.
- **Search-wide K.** `k_scope: instrument` counts the instrument's distinct ledgered cards for 5f; `k_scope: ledger` counts every instrument's. Reports carry `k` and `k_scope`. By [ruling](../../docs/briefs/pre-registration/2026-11-01-builder-r1-mcl-orb-registration.md) (Joshua 2026-11-03, recorded 2026-11-08), R1's re-registration records its K in a `register_search` manifest in `discovery_manifests/`, the candidate contract's sole machine K ledger.
- **Reachability line (report-only).** After the cards are ledgered and the split resolved, and before any card is evaluated, `run.py` prints each instrument's `gates.reachability(k, n)` and writes it into every report as `reachability_5f`. It gives gate 5f's floor at the K 5f will use (banked, per `k_scope`) and the development-session count n: per session `(E[max Z_K] + 1.645)/√(n−1)` and ×√252 annualised, the normal-approximation P(pass) at a true annual Sharpe of 0.85 and 0.89, and `reachable` (annual floor ≤ 0.89). This is the standing power disclosure of [ADR 2026-07-12 §2.4](../../docs/adr/2026-07-12-dsr-k-rule-and-variance-floor-supersession.md) under the D7 rule (generation-phase note §9.2, PR #1029). It is a description only and never changes a gate, a threshold or a verdict.
- **Holdout runner.** `run.binding` is every development input in canonical form: run.yaml's fields with each file reduced to its pinned sha256 (paths and `out` excluded), the card hashes, the resolved per-instrument costs and the engine sha256. `verdict.json` carries it and its sha256 with each report's sha256; it is deleted before a run ledgers and written last by an atomic rename. Every report carries the binding sha256. The holdout refuses, before any look, unless the current run.yaml recomputes to that sha256 (naming the changed fields), every listed report matches its sha256 and is final for this run_id. Survivors are the `survivor` reports; each look is ledgered before its holdout bars are simulated.
- **Gate labels.** The timing placebo is reported as `5e placebo_rank (timing-only, not the mechanism discriminator; same-day window slide of the clock frame)` and 5b as `5b costs applied (not a gate)` (`gates.py:34-35`).
- **5e is a same-day window slide (lesson M-17; Joshua 2026-11-04).** For each Δ ≠ 0 (15m bars), `gates.slid` moves the card's whole clock frame: the range offset (a `first_n_bars` range becomes the equivalent `time_window`), `entry_cutoff` and `flat_at`; every other rule is the card's. Δ is in the slide set S when the offset is ≥ 0, the timing is valid and the first 15m bar open at or after `flat_at` is before 17:00 (no bar exists at 17:00, so such a slide could resolve only its stopped trades). Each slide runs through `compile.py` on the development sessions, so a slid trade's side comes from its own breakout. Each of `5e_placebo_runs` runs draws one window per session from S and the card's own (Δ = 0), uniformly, and sums; the beaten share is the share of runs below the card's net. Drawing Δ = 0 makes the null exact: under per-session exchangeability of the window nets, the card's total and a run's total are identically distributed, so the zero-edge false pass is the nominal 0.05 for any |S|. A slid session that is skipped or unresolved contributes 0 and is counted (`slid_skipped_sessions`, `slid_unresolved_sessions`). 5e fails closed, with a `reason`, when |S| (slides other than Δ = 0) < `gates.SLIDE_MIN` (2) or the null has zero variance. `run.py` prints each card's `gates.slide_line` (|S|, the windows drawn and the slid span) beside the reachability line, before any card is evaluated, and every report carries it as `slides_5e`. It replaced the timing shuffle, which kept the realised side, so a draw before the breakout rode the move that chose the side (#1067).
- **5g is placement, not a kill (branch B, Joshua 2026-11-04).** The development verdict is 5a–5f (`gates.py:297-311`). After a holdout pass, `holdout_look` runs 5g on the development-window book statistics already in the card's report (`gates.py:396`, `:426-427`), so no new data is read, and writes `placement: clear | fail` with `placement_gate` (value, threshold, pass) and `placement_book_sha256` (run.yaml's pinned book) into `<card id>.holdout.json`, inside the same `dev_binding_sha256`. The look's verdict is never changed by it: a pass with `placement: fail` reads as CONFIRMED · VENUE-FAIL(edition) ([§Confirm verdicts](../../docs/adr/2026-08-30-evaluation-order.md#confirm-verdicts)) once the coordinator adjudicates CONFIRMED. Without a pass, `placement` is null. A declared empty book (`book: null`) gives `placement: not_evaluated` with no gate record, never a clear; a supplied book with no overlapping development session, or with no losing day in the overlap, fails closed. Malformed book statistics in any survivor's report, or statistics that disagree with run.yaml on whether a book was supplied, are refused before the first look (`holdout.py:77-78`, `gates.py:364`, `:377`, `:416-417`). Gate 5h (`venue.py`) is where a venue check would attach to this stage later; it is not wired. `run.py`'s `min_overlap` check still runs before any card is evaluated (`run.py:188`). Fit uses development-window overlap only; holdout-window book overlap is not read.
- **Thresholds.** They change only by PR with Joshua's approval, and a pre-registration freezes them before any card runs.
- **Costs.** Commission comes from `FIRM_RULES` through `discovery.cost_model.resolve_commission` (MCL and MGC are per-symbol rows at Tradeify and MFFU). An explicit `commission_per_side` is accepted only for an instrument without a firm row, must be positive, and is cited in the pre-registration. Every result carries a slippage of 1 tick per side.
- **The book's per-session Sharpe** with the card added is reported for every card. It is a description, not a gate.

Real ledgers, data, run files and reports are private. Keep them outside the repo, for example in `local_artifacts/strategy-builder-2026-10/`.

## Ledger integrity

- **What is detected.** The chain catches an edited, reordered or interior-deleted entry. The head anchor `<ledger>.head` (`{seq, entry_sha256}` of the last entry, replaced atomically after each append) catches a valid-prefix rollback: a truncated tail, an older copy of the ledger or a deleted ledger. `read` refuses a non-empty ledger without an anchor, a ledger that lacks the anchor's seq with that hash, and a ledger longer than its anchor. Every reader (K, `contains`, the one-look check) goes through `read`, so a rollback can neither respend a look nor shrink K.
- **Crash order.** The ledger line is written and fsynced, then the anchor is replaced. A crash between the two leaves the ledger one append past its anchor; that is refused like a rolled-back anchor, never accepted silently, until the operator checks the tail and runs `adopt-head --confirm`.
- **Atomic admission.** `append_cards` and `append_holdout_look` hold `exclusive_file_lock` (`<ledger>.lock`, beside the ledger) across the read, the checks, the seq/prev computation, the append and the anchor update; `read` takes the same lock. Two callers racing for one look get exactly one winner; the other raises `LedgerError` before any holdout bar is simulated.
- **Run head.** `builder.run` records the ledger head just after its cards were appended in `verdict.json` (`ledger_head`, outside `binding_sha256`, since later rounds keep appending). `builder.holdout` refuses unless the ledger still holds that seq with that hash, and refuses if any survivor already has `out/<card id>.holdout.json` (defence in depth: that file can be deleted).
- **Limit.** The anchor sits beside the ledger, so restoring the ledger and its anchor together (a whole-folder restore from an older backup) is not detected by the ledger. The run head catches it only when that run's `out` was not restored with them.
- **Existing ledgers.** A ledger written before the anchor existed is refused until bootstrapped once, in Joshua's primary session: `python -m builder.ledger adopt-head <ledger>` prints the entry count and head; check them against his records, then rerun with `--confirm <entry_sha256>`. A read never creates an anchor, and `adopt-head` will not overwrite an anchor the ledger does not hold. A development marker (`out/verdict.json`) written before `ledger_head` existed is refused with its own message; rerun `builder.run` to regenerate it (it re-appends the same card hashes, so K is unchanged) before running the holdout.

## Gate 5h: venue MC (`venue.py`)

Settings are pinned by the research coordinator's ticket (2026-11-01) and live as module constants:
`Tradeify_Select_100K` (consistency 0.40) and `MFFU_Rapid_100K` (0.50) through `mc.preflight.firm_kwargs` with inactivity on, a $100,000 fresh account, fixed size and no protection (`dd_trigger=10.0`, `dd_scale=1.0`), seeds 20261101-20261110 at 1,000 paths each. The panel is every weekday in the window shared by the book and the candidate, zero where a leg has no session, cut to complete Mon-Fri weeks. The book is used as given; the candidate's per-trade points are priced per config like gate 5b (firm commission + 1 tick per side). Every run, book alone and book plus candidate, carries a **preservation leg**: minus one micro MNQ round trip at the config's costs on the first weekday (Monday) of each complete week, standing in for the operator's weekly preservation trade, so that day is active. `gating_bust` = headline bust + inactivity bust; horizon-cap paths are reported, not counted.

The gate is relative (thresholds approved by Joshua 2026-11-01). Book alone and book plus candidate run on the same seeds and weeks, so each path draws the same weeks in both (common random numbers). A candidate passes when, in both configs, `gating_bust` rises by at most `VENUE_THRESHOLDS["5h_max_bust_increase"]` (0.01) and P(pass) falls by at most `VENUE_THRESHOLDS["5h_max_pass_decrease"]` (0.01). `book_bust_target` (0.05) is reported as `book_target_met` for the book alone and with the candidate; it never gates a candidate. A book-alone run's verdict is `baseline`. A config the preflight or the cost table refuses gives `refused`. P(payout) is not encoded. Every result is an end-of-day research screen: venues enforce drawdown intraday and this panel has no intraday path.

Book alone: `python -m builder.venue --book <json> --sha256 <hex> --out <json>` (with `lab` and `core` on the path). Results are private, like every other builder output.
